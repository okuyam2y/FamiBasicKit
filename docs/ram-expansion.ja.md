# プログラム領域を広げる — 詳細

[English](ram-expansion.md)

このファイルは「何をどう書き換えているか」「なぜそれで足りるのか」の説明です。
使い方は [README](../README.ja.md) を見てください。

## 1. 上限を決めているのは RAM の量ではない

ファミリーベーシックは、起動時にゼロページ `$03/$04` へ「**領域の最後の番地**」を入れます。
この値は ROM に焼かれた即値で、**機材にいくら RAM が載っていても関係ありません**。

`BYTES FREE` の表示も、`CLEAR` で確保できる上限も、全部この2バイトから来ています。
∴ ここを書き換えるだけで領域が広がります。

書き換えるのは2箇所です。

1. **起動時の初期化** — ゼロページ `$03/$04` に入れる即値
2. **`CLEAR` 文の引数チェック** — 「この番地以上ならエラー」という決め打ちの上限

⚠️ **V1.0 だけ `$03/$04` の意味が「最後の次の番地」**（`$7800`）です。V2/V3 は
「最後のバイトの番地」（`$77FF` / `$6FFF`）。直前に `LDA #$FF / STA $03` があるかで見分けます。
`fb-expand-basic-area.py` は自動で判別します。

| 版 | 元の領域 | 広げた後 |
|---|---|---|
| V1.0 / V2.0A / V2.1A | `$7000-$77FF`（2KB） | `$7000-$7FFF`（4KB） |
| V3.0 | `$6000-$6FFF`（4KB） | `$6000-$7FFF`（8KB） |

**上限が版で違うのは、領域の先頭が違うから**です。V1/V2 は先頭が `$7000` なので、
先頭を動かさない限り `$7FFF` まで伸ばして 4KB。V3 は先頭が `$6000` なので 8KB 取れます。

### iNES ヘッダも1バイト変える

PRG を書き換えても、機材が RAM を用意してくれなければ意味がありません。
NES 2.0 ヘッダの **10 バイト目の上位ニブル**が NVRAM のサイズです
（`5`=2KB / `6`=4KB / `7`=8KB / `8`=16KB）。

| 変更 | ヘッダ byte10 |
|---|---|
| V1/V2 を 4KB に | `$50` → `$60` |
| V3 を 8KB に | `$60` → `$70` |

∴ **合計の変更量は PRG 2バイト＋ヘッダ 1バイト**です。

`fb-expand-basic-area.py` はこの3バイトをまとめて書き換えます（宣言を倍にする）。
ヘッダを触らせたくない場合は `--keep-header` を付けますが、**その ROM は実機で効きません**。

### ⚠️ 触ってはいけない場所

**V3 の `$ADC8` 付近にある「ROM から内蔵プログラムを領域いっぱいにコピーするループ」の
終わりの番地は伸ばさないこと。** 伸ばすとコピー元が ROM を越えて読み進め、最悪 PPU の
レジスタを読んでしまいます。領域の終端は `$03/$04` で管理されているので、ここを伸ばす
必要はありません。

## 2. なぜ 8KB までは MMC5 が要らないのか

`$6000-$7FFF` の 8KB は、**カートリッジが RAM を置いてよい窓としてもともと空いています**。
マッパー0（NROM）は「バンク切り替え機構を持たない」というだけで、この窓に実 RAM を
置くことを妨げません。

実カートの V1/V2 が 2KB、V3 が 4KB なのは載っている SRAM チップの都合で、
残りはミラー（折り返し）です。

- V2 の 2KB → `$6000-$67FF` / `$6800-$6FFF` / `$7000-$77FF` / `$7800-$7FFF` の4面
- V3 の 4KB → `$6000-$6FFF` / `$7000-$7FFF` の2面

∴ **ヘッダの宣言どおりに RAM を用意する機材なら、マッパー0 のまま 8KB まで届きます。**
逆に言えば、**実カートでは拡張版は意味がありません**（折り返して同じ場所を指すため）。

| 目標 | 要るもの |
|---|---|
| V1/V2 を EverDrive で起動させる | **ヘッダを付けるだけ**（ヘッダ欠落が `Unformatted ROM` の原因） |
| V1.0 を 4KB に | PRG 2B ＋ ヘッダ 1B |
| V2.1A を 4KB に | PRG 2B ＋ ヘッダ 1B |
| V3 を 8KB に | PRG 2B ＋ ヘッダ 1B |
| **V3 を 16KB に** | **MMC5**（`$8000-$9FFF` にも RAM を割り当てる） |

⚠️ `BYTES FREE` は**プログラムが空のときの満額**です。`.sav` を読ませた状態
（`BASIC HOT START`）だとそのぶん減ります。数字を比べるときは条件を揃えてください。

## 3. 16KB 版 — BASIC 本体を引っ越す

`$6000-$7FFF` の 8KB 窓を使い切ってしまうと、次は `$8000` 以降に RAM を置くしかありません。
そこは本来 PRG-ROM の場所なので、**バンク切り替えを持つマッパー（MMC5）が要ります**。
そして `$8000-$9FFF` に載っている **BASIC 本体 8KB の置き場所が無くなります**。

空けられるのは `$D400-$FFF9` にある**内蔵プログラム4本**（音楽デモ＋ゲーム3本）の場所だけです。
∴ 本体をそこへ引っ越し、内蔵プログラムはバンクへ追い出します。

⚠️ **8KB と 16KB の中間はありません。** RAM を貼れる単位が 8KB なので、12KB という
選択肢は存在しません。

### 電源投入後のメモリ地図

| CPU から見える所 | 中身 |
|---|---|
| `$6000-$7FFF` | WRAM ブロック0（フリーエリア前半） |
| `$8000-$9FFF` | **WRAM のもう1ブロック**（後半。番号は起動時に判定する→[mmc5-wram-banks.md](mmc5-wram-banks.ja.md)） |
| `$A000-$BFFF` | ROM バンク5（元のまま。1バイトも動かしていない） |
| `$C000-$DFFF` | ROM バンク6（元の `$C000-$CFFF` ＋ 引っ越した本体の前半） |
| `$E000-$FFFF` | ROM バンク7（本体の後半 ＋ 背景画 ＋ 初期化 ＋ ローダ ＋ ベクタ） |
| バンク0-3 | 内蔵プログラム1本ずつ（下半分は `$C000-$CFFF` の複製） |

### `$5117` を触らなくてよいようにしてある

MMC5 の `$5117` は電源投入時の初期値が `$FF`＝ROM の最終バンクです。
**初期化コードとベクタをその最終バンク（バンク7）に置いた**ので、電源投入直後から
正しいものが見えています。

これにより「`$5117` を書いた瞬間に、いま実行中のコードが載っているバンクが差し替わる」
という MMC5 の定番の罠を、そもそも踏まずに済みます。

### 内蔵プログラムの読み込み

**1本につき 8KB バンクを1枚**使い、その上半分（`$D000-$DFFF`）にプログラムを置きます。
読み込みループは行き先が `$7000` に届くまで（最大 4,090 バイト）読み続けますが、
4,090 < 4,096 なので**バンクの外へはみ出しません**＝バンクをまたぐ処理が要りません。

バンクの下半分には `$C000-$CFFF` を複製してあります。`$5116` で差し替わるのは 8KB 単位なので、
複製しておけば**差し替え中に消えるのは `$D000-$DFFF` だけ**になります。

⚠️ **差し替えている間は NMI を止めます。** 消える `$D000-$DFFF` に NMI 処理の本体
（引っ越し後 `$D971`）があるためです。

⚠️ **戻すときは `LDA $32 / ORA #$80 / STA $2000`。** `$32` は BASIC が持っている `$2000` の
控えですが、**bit7（NMI 許可）を持っていません**。`LDA $32 / STA $2000` だと NMI が
止まったままになり、画面もキーも死にます（実機で一度そうなりました）。

なお、元の `GAME` にあった「ROM の終わりを越えて読み進み、`$0000` 側へ回り込んで
PPU/APU のレジスタを読む」危険は、16KB 版では消えています（バンク内で完結するため）。

### `.sav` は 32KB になる

16KB 版の `.sav` は **32KB** で、8KB 版とは互換がありません。
ブロック0が `$6000-$7FFF`、ブロック1が `$8000-$9FFF` に対応します。

（MiSTer の NES コアの場合、`prg_nvram != 7` だと `save_sz` が 32KB になるため。
`./tools/fb-basic-to-sav.py -V v3 --16k` がサイズを自動で合わせます）

## 4. 引っ越しで直したもの

`$8000-$9FFF` を別の番地へ動かすと、そこを指している値を全部直さなければなりません。
**全数を数えた結果**（V3 の現物での実測）:

| 種類 | 件数 | 見つけ方 |
|---|---|---|
| 絶対番地の `JSR`/`JMP`/データ参照 | 860 | 逆アセンブルした命令のオペランド |
| 相対分岐 | 479 | **直さない**（行き先も一緒に動くよう範囲を伸ばしてある） |
| 番地表の項目 | 4表 | `LDA 表,X / STA $19 / LDA 表+1,X / STA $1A / JMP ($0019)` の形 |
| 即値2つで組み立てた番地 | 2 | `LDA #<lo / STA zp / LDA #>hi / STA zp+1` |
| リセット／IRQ ベクタ | 2 | `$FFFC` / `$FFFE` |

⚠️ **静的に辿れるのは ROM の一部だけ**なので、「バイト列が `$80xx-$9Fxx` に見えるから
番地だろう」で探すと**データを壊します**。実際に踏んだ落とし穴は
[relocation-notes.md](relocation-notes.ja.md) にまとめてあります。

`fb-relocate.py` は**入力が素の V3 でなければ止まります**（PRG+CHR の SHA-256・3本のベクタ・
未定義オペコードの位置・断片の入口を固定）。

## 5. 検証の仕方

「エラーが出なかった」は検証ではありません。この作業では次の3つを使いました。

- **`fb-mmc5-16k.py` に組み込んだモデル実行** — 6502 と MMC5 のバンク切り替えを最小限
  モデル化して、**組んだ起動時判定を実際に走らせます**（`WRAM_MODELS`）。
  バンク番号の解釈を `linear` / `chip` / `only8k` の3通りに差し替えて、それぞれで
  どう転ぶかを組み立て時に毎回表示します。
  `$5114-$5116` の電源投入時の値は**不定**なので、「未設定」を毒として扱い、
  設定前に `$8000-$DFFF` を参照したらその場で失敗させます
- **`fb-basic-to-sav.py --selftest`** — ROM 内蔵プログラム4本（387 行・8,999 バイト）を
  復号 → 再変換して**1バイトも違わない**ことを求めます。
  **正解を自分の理解に置かない**ための作りです
- **素の ROM との画面の突き合わせ** — 引っ越しの欠陥は「めったに通らない経路だけが
  静かに壊れる」形で出ます。∴「動いた」ではなく「**改造していない素の V3 と同じ画面になる**」
  で確かめました。`tests/basic/` のプログラムはそのために書いたものです。
  素の V3 のフリーエリアは 4KB なので、そこに収まらない大きさは
  `fb-gen-bigtest.py`（答えが計算で分かるプログラムを作る）で当てます

実際、**多重レビューで実機に載せた ROM の欠陥が2件出ました**。どちらも生成物は正常に見え、
静的な検算を全部通り、普段の操作では再現しませんでした。
