# 絵を見る・差し替える — ROM の中のタイル 8KB

ファミリーベーシックが画面に出せる絵は、`MOVE` で動かすキャラクタも、英数字も、かなも、
**`.nes` ファイルの末尾にある 8KB** に入っています。8×8 ピクセルのタイルが 512 枚、
1 ピクセルは 4 階調です。索引も圧縮もありません。タイル番号 `n` の絵は、`n × 16`
バイト目から 16 バイトです。

| タイル番号 | 中身 |
|---|---|
| 0〜255 | スプライトのキャラクタ 16 種類 |
| 256〜511 | 文字。文字コード `c` の絵はタイル `256 + c`（`A` は `256 + 65`） |

**どのバージョンでもこの 8KB は同じです。** V1.0・V2.0A・V2.1A・V3.0 の 4 つのダンプで
1 バイトも違いません（`ec06b3c44be7ee18133e3d32c82465dc`）。差し替えた絵は 1 枚作れば
どのバージョンでも使えます。

⚠️ **ディスク版にはこの 8KB がありません。** ディスク版はタイルを RAM に置き、起動時に
ディスクから読み込みます。ファイルの中に書き換える対象がありません。

## 見る

    $ ./tools/fb-chr.py "Family BASIC V3 (Japan).nes" --sheet tiles.png
    $ ./tools/fb-chr.py "Family BASIC V3 (Japan).nes" --index characters.png
    $ ./tools/fb-chr.py "Family BASIC V3 (Japan).nes" --map
    $ ./tools/fb-chr.py "Family BASIC V3 (Japan).nes" --show 4

`--sheet` は 512 枚を 128×256 の PNG に書き出します。横 16 枚・縦 32 段で、拡大も縮小も
しません。エミュレータのタイル閲覧画面と同じ並びです。`--index` はキャラクタ 16 種類の絵を
`SPRITE()` に渡す番号つきで 1 枚にまとめます。`--show` は 1 体分を向きごとに端末へ描きます。

## 差し替える

    $ ./tools/fb-chr.py "Family BASIC V3 (Japan).nes" --apply tiles.png -o "V3 (new art).nes"

4 階調の色は `#FFFFFF`・`#AAAAAA`・`#555555`・`#000000` です。階調 0 はスプライトでは透明、
文字画面では背景色になります。完全に透明なピクセルは階調 0 として読むので、消しゴムで
消した場所はそのまま透明になります。

色はこの 4 色ちょうどでなければいけません。アンチエイリアスがかかったり、
別のパレットに変換されたりすると中間色ができ、道具は当て推量をせずに止まります。
`--snap` を付けると「いちばん近い 1 色に寄せる」動作になり、何ピクセル動かしたかを表示します。

### ★ 絵の差し替えは最後に

組み上がった ROM に新しい絵を入れるのは問題ありません。プログラムもヘッダもそのまま残り、
実際に新しいタイルが画面に出ます（2026-08-31 にエミュレータで確認。NROM 8KB 版・
MMC5 16KB 版・VRC7 版の 3 つ）。

逆の順序はできません。`fb-relocate.py` と `fb-vrc7.py` は入力の照合にタイルを含めた
ダイジェストを使い、`fb-mmc5-16k.py` は 2 つの入力のタイルが同じであることを求めます。
3 つとも、絵を触ったダンプを受け付けません。この照合があるから決め打ちの番地に安全に
書き込めるので、作業の順序はこうなります。

    ダンプ → ビルドする → 絵を差し替える

（`fb-expand-basic-area.py` はダイジェストを持たないので、絵を差し替えたダンプも受け付けます。
NROM 8KB 版だけでよければこの順でも作れます。）

⚠️ **絵を変えると ROM の MD5 が変わります。** この repo に記録してある値
（16KB 版の `541f9769bd5c0243c29d7a2f5d72c177` など）は**元の絵のときの値**です。
新しい絵で組んだ ROM がその値と違うのは、壊れたのではなく当たり前です。

## どのタイルがどのキャラクタか

`SPRITE(c, ...)` のキャラクタ番号は 0〜15 です。1 体は 2×2 の 4 枚で描かれ、
どの 4 枚を使うかの表が ROM の中にあります。`--map` はその表を、渡された ROM から読みます。

| c | タイル | | c | タイル |
|---|---|---|---|---|
| 0 | `$00-$0F`, `$14-$1B` | | 8 | `$98-$A3` |
| 1 | `$1C-$2B`, `$30-$37` | | 9 | `$A4-$AF` |
| 2 | `$38-$3F` | | 10 | `$B0-$B7` |
| 3 | `$40-$57` | | 11 | `$58-$5F` |
| 4 | `$60-$6F` | | 12 | `$D0`, `$D2`, `$D4`, `$EF` |
| 5 | `$70-$77` | | 13 | `$B8-$BF` |
| 6 | `$78-$8F` | | 14 | `$C0-$C7` |
| 7 | `$90-$97` | | 15 | `$C8-$CF` |

同じタイルを 2 体が使うことはありません。実際に描かれるタイル番号は

    タイル番号 = 表の 4 枚 + キャラクタごとの加算値 + 4 × アニメの駒数

です。アニメの次の駒は 4 枚先にあります。キャラクタごとの加算値だけが違って表を共有する
組み合わせがあり、キャラクタ 2・7・10・11・14 の 5 体は同じ 9 通りの表を
別々の加算値で読んだものです。

### 表の見つけ方と、そろっていない 2 か所

表は**番地ではなく形で**探します。16 個のポインタがあり、その先がそれぞれ 3 個のポインタ、
その真ん中が 9 個のポインタ（向き 1 つに 1 個）、その先が 4 枚のタイル番号。
この形をしている場所は ROM の中に 1 つしかありません。番地で探せないのは、
バージョンによって場所が動くからです（V3.0 は `$C709`、V1.0 と V2.x は `$BC75`）。

* **アニメの駒数の入れ方がバージョンで違います。** V1.0 と V2.x は 16 倍した値を持ち、
  反転の指定は別の表にあります。V3.0 は 1 バイトに詰めていて、下位 4 ビットが駒数、
  ビット 6 と 7 が反転です。数字そのものはどちらも同じです。読み方を間違えると、
  どのキャラクタもタイルが 1 枚も出てきません。
* **キャラクタ 0・1・4 には、表に載っていない 2 コマ目があります。** 向き 1 と 5
  （上り・下り）のとき、ROM はプログラムの中に書かれた 4 枚を指します。中身は 1 コマ目と
  同じ 4 枚を左右反転しただけなので、使うタイルは増えません。ただし、ほかの向きと同じに
  「4 枚先」と数えると、別のキャラクタのタイルを指してしまいます。実際、
  キャラクタ 4 がキャラクタ 5 に食い込みます。

どちらも決め打ちにしていません。読み方がずれたら必ず落ちる 2 つの条件で押さえています。
1 つは **16 体のタイルが重ならないこと**（コードが差し替える所で「4 枚先」と数えると、
キャラクタ 4 がキャラクタ 5 に食い込みます）。もう 1 つは
**どのダンプから読んでも同じ結果になること**です。バージョンが違えばプログラムの番地は
全部違うので、後者はそれ自体が答え合わせになります。

## 検査が何に立っているか

書き出して、戻して、ファイルを比べる。この往復検査では、**読みと書きで同じ間違いをしている
場合**を捕まえられません。1 タイルは 2 枚の面（bit plane）でできていて、この 2 枚を
取り違えて読み、取り違えて書けば、ファイルは 1 バイトも変わらないまま、
画面に見せていた絵だけが階調 1 と 2 が入れ替わったものになります。

そこで階調の意味は、別の人が書いた資料に合わせてあります。NESdev Wiki のパターンテーブルの
ページ（<https://www.nesdev.org/wiki/PPU_pattern_tables>）に、16 バイトと、それが描く 8 行の
階調が載っています。検査は毎回このバイト列を復号して比べ、さらに符号化して戻します。
実際にこの検査が効いているかは、面を読み・書きの両方で入れ替えてみて落ちることで
確かめてあります。往復検査はここを見逃します。
