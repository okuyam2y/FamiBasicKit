# 絵を見る・差し替える — ROM の中のタイル 8KB

ファミリーベーシックが画面に出せる絵は、`MOVE` で動かすキャラクタも、英数字も、かなも、
**`.nes` ファイルの末尾にある 8KB** に入っています。8×8 ピクセルのタイルが 512 枚、
1 ピクセルは 4 階調です。索引も圧縮もありません。タイル番号 `n` の絵は、`n × 16`
バイト目から 16 バイトです。

| タイル番号 | 中身 |
|---|---|
| 0〜255 | スプライトのキャラクタ 16 種類 |
| 256〜511 | 文字。文字コード `c` の絵はタイル `256 + c`（`A` は `256 + 65`） |

**どのバージョンでもこの 8KB は同じです。** V1.0・V2.0A・V2.1A・V3.0 の 4 つのダンプで
1 バイトも違いません（`ec06b3c44be7ee18133e3d32c82465dc`）。差し替えた絵は 1 枚作れば
どのバージョンでも使えます。

⚠️ **ディスク版にはこの 8KB がありません。** ディスク版はタイルを RAM に置き、起動時に
ディスクから読み込みます。ファイルの中に書き換える対象がありません。

## 見る

    $ ./tools/fb-chr.py "Family BASIC V3 (Japan).nes" --sheet tiles.png
    $ ./tools/fb-chr.py "Family BASIC V3 (Japan).nes" --index characters.png
    $ ./tools/fb-chr.py "Family BASIC V3 (Japan).nes" --map
    $ ./tools/fb-chr.py "Family BASIC V3 (Japan).nes" --show 4

`--sheet` は 512 枚を 128×256 の PNG に書き出します。横 16 枚・縦 32 段で、拡大も縮小も
しません。エミュレータのタイル閲覧画面と同じ並びです。`--index` はキャラクタ 16 種類の絵を
`SPRITE()` に渡す番号つきで 1 枚にまとめます。`--show` は 1 体分を向きごとに端末へ描きます。

## 差し替える

    $ ./tools/fb-chr.py "Family BASIC V3 (Japan).nes" --apply tiles.png -o "V3 (new art).nes"

4 階調の色は `#FFFFFF`・`#AAAAAA`・`#555555`・`#000000` です。階調 0 はスプライトでは透明、
文字画面では背景色になります。完全に透明なピクセルは階調 0 として読むので、消しゴムで
消した場所はそのまま透明になります。

色はこの 4 色ちょうどでなければいけません。アンチエイリアスがかかったり、
別のパレットに変換されたりすると中間色ができ、道具は当て推量をせずに止まります。
`--snap` を付けると「いちばん近い 1 色に寄せる」動作になり、何ピクセル動かしたかを表示します。

### ★ 絵の差し替えは最後に

組み上がった ROM に新しい絵を入れるのは問題ありません。プログラムもヘッダもそのまま残り、
実際に新しいタイルが画面に出ます（2026-08-31 にエミュレータで確認。NROM 8KB 版・
MMC5 16KB 版・VRC7 版の 3 つ）。

逆の順序はできません。`fb-relocate.py` と `fb-vrc7.py` は入力の照合にタイルを含めた
ダイジェストを使い、`fb-mmc5-16k.py` は 2 つの入力のタイルが同じであることを求めます。
3 つとも、絵を触ったダンプを受け付けません。この照合があるから決め打ちの番地に安全に
書き込めるので、作業の順序はこうなります。

    ダンプ → ビルドする → 絵を差し替える

（`fb-expand-basic-area.py` はダイジェストを持たないので、絵を差し替えたダンプも受け付けます。
NROM 8KB 版だけでよければこの順でも作れます。）

⚠️ **絵を変えると ROM の MD5 が変わります。** この repo に記録してある値
（16KB 版の `541f9769bd5c0243c29d7a2f5d72c177` など）は**元の絵のときの値**です。
新しい絵で組んだ ROM がその値と違うのは、壊れたのではなく当たり前です。

## 実行中に絵を差し替える

`--apply` で差し替えた絵は、電源を入れてから切るまで変わりません。ROM から読んでいるので、
プログラムの側からは手が出せません。自分で描いた絵を使うプログラム（駒を描く盤ゲーム、
自前の文字で書いたタイトル画面）には、タイルが RAM に載っている必要があります。

⚠️ **ここで作れるビルドのうち、そうなっているのは 2 つです。** どちらも、ファイルの中には
書き換える対象がありません。

* **ディスク版**。ディスクシステムは 8KB のキャラクタ RAM を持っていて、起動時に
  ディスクから絵を読み込みます。
* **`--chr-ram` を付けて組んだ 16KB の MMC5 版**（`./tools/fb-mmc5-16k.py ... --chr-ram`）。
  この ROM は絵を ROM ではなく RAM として宣言し、絵そのものは PRG の空きバンクに載せて、
  電源投入時にコピーします。

上に書いた「ファイルの中に書き換える対象がない」は裏返すと、
**BASIC が動いている最中に絵を差し替えられるビルド**だということです。

    $ ./tools/fb-chr.py "Family BASIC V3 (Japan).nes" --sheet tiles.png
    ... tiles.png を描き替える ...
    $ ./tools/fb-pcg.py "Family BASIC V3 (Japan).nes" tiles.png -o pcg.bas

`fb-pcg.py` は、描き替えた PNG を ROM のタイルと突き合わせて、**違っているタイルだけを
組み込む BASIC のプログラム**を書き出します。同じままのタイルは入りません。
描き替えが小さければ、プログラムも小さくなります。

新しい命令も、書き換えた ROM も要りません。ファミリーベーシックには入口が 2 つあります。
`POKE` でフリーエリアの上端に短い機械語を置き、`CLEAR` で BASIC がそこへ
入らないようにし、`CALL` で呼びます。機械語は NMI を止め、垂直帰線期間を待ち、
PPU をタイル 1 枚に向けて 16 バイト書き、**戻せる場合はスクロールを戻して**から NMI を
戻します。16 バイトは帰線期間に余裕で収まるので、画面表示は一度も止めません。

⚠️ **スクロールを戻すのは、行儀の問題ではありません。** この機械では、ビデオメモリの
番地を指すレジスタが**そのままスクロールのレジスタ**です。しかも BASIC は毎フレーム
スクロールを書き直しているわけではなく、次に何かを描くときにだけ書きます。戻さないと、
そのときまで画面はずれたままになります。エミュレータで測ると**画面の 19% が 10 フレーム
のあいだ違い**、BASIC が文字を出した瞬間に元へ戻りました。ルーチンは BASIC 自身が
持っているスクロールの値を読んで戻すので、0 ではなく元の位置へ戻ります。

⚠️ **戻せるのは V3 のダンプから作ったときだけです。** 戻すには BASIC がその値をどのバイトに
置いているかを知っている必要があり、それが分かっているのは V3 だけです。V2.1A から組んだ
ディスクに V3 の番地で試したところ、画面の 5 分の 1 がずれたままでした（番地が別の場所に
あります）。そこで V2 のダンプから作ったプログラムは**書き戻しを入れずに**出し、道具がそのことを
表示します。画面は BASIC が次に描くまでずれたままになりますが、これは書き戻しが無いときと
同じで、**誰も確かめていない番地の値を PPU に書くことだけはしません**。V2 系のスクロールが
どこにあるかを測れば、この制限は無くなります。

NROM 版・`--chr-ram` を付けない MMC5 版・VRC7 版では、同じプログラムが最後まで走り、
**絵は変わりません**。キャラクタ ROM への書き込みは基板が黙って捨てるので、エラーも出ません。
画面には何の手がかりも出ないまま、絵だけが元のままになります。

⚠️ **`--chr-ram` は既定ではありません。理由があります。** エミュレータ・MiSTer・
EverDrive N8 PRO を挿したファミコンの 3 つでは絵が出ることを確かめましたが、絵を RAM にした
MMC5 のカートリッジは市販されたことがなく、それ以外の機械では試していません。宣言が
受け付けられない機械では、**絵が違うのではなく絵が無い**（画面が砂嵐になる）ので、
既定にはせず、指定したときだけ別のファイルとして出すようにしてあります。

### どれくらい入るか

タイル 1 枚は `DATA` の数値 18 個です（行き先の番地が 2 個と、絵の 16 バイト）。
道具は書き出したプログラムを ROM 自身の予約語表と、**そのバージョンの数字の持ち方**
（V3 は 0〜9 を 1 バイト、V2 系は 3 バイト使う）でトークン化し、
**BASIC が実際に何バイトで持つか**を表示します。入らないものは書き出さずに止まります。

使えるのはフリーエリア全部ではありません。引かれるものが 2 つあります。10 行目が
いちばん上の 1 ページをルーチンに渡してしまう分と、**このプログラム自身の変数の分**です。
変数はプログラムの後ろに置かれるので、ぎりぎり入る大きさだと最初の代入で `?OM ERROR` になり、
絵は 1 枚も入りません。いくら要るかは推測せず `FRE` で機械に訊いてあります。

⚠️ **V3 のビルドでは、さらに 1KB 引かれます。** `BGGET` と `BGPUT` が共有する 1KB の
画面バッファがフリーエリアのいちばん上にあり、そこはルーチンの置き場所と重なります。
16KB 版でルーチンを上端に置いて測ると、`BGGET` と打っただけで `OK` が返り、
**ルーチンの先頭 64 バイトのうち 55 バイトが画面の内容で上書きされました**。
エラーも警告も出ず、次の `CALL` は画面のデータを実行することになります。そこで
ルーチンはこの 1KB の下に置き、`CLEAR` は 256 バイトではなく 1,280 バイトを返します。
V2 系には `BGGET`・`BGPUT` が無いので、返すのは 1 ページだけです。

    3 tile(s) differ from Family BASIC V3 (Japan).nes: $00, $14B, $14F
      routine at $7B00, tile buffer $7B40, CLEAR $7AFF
      $7C00-$7FFF left alone: BGGET/BGPUT write their screen buffer there
      N lines / N bytes as V3 stores it (N left of N: N free, less what CLEAR takes
      back and what the program's own variables need)

⚠️ **数字はこのページのものではなく、道具のものです。** ルーチンの長さやフリーエリアが
変われば動きます。ここに書き写したページは黙って間違ったものになります（実際、この道具の
レビュー中に 2 回そうなりました）。実際の数字は道具を動かして読んでください。

フリーエリアの出発点だけは書いておきます。これは機械自身が表示する数字で動かないためです。
`$7FFF` で終わるフリーエリアなら、V3 から組んだディスクは `8182 BYTES FREE`、V2.1A から
組んだディスクは `8126` です。既定はバージョンだけでなく `--top` にも従うので、
フリーエリアを狭くすればこの数字も小さくなります。プログラムの開始番地が別の配置に
当てるときは `--area` で指定します。

書き出す前に、道具は**自分が書いたプログラムを読み直して実行します**。6502 のモデルの上で
`DATA` の数値を順に配り、16 バイトずつ書き込ませ、結果が描き替えた PNG と一致するかを見ます。
`DATA` から数値が 1 つ落ちた、タイルの行き先が 1 枚ずれた、といった間違いは、
「走るけれど違う絵を描くプログラム」になる前に止まります。

2026-08-31 にエミュレータで確認しました。V3 から組んだディスクでプログラムを走らせると、
キャラクタ RAM の 8,192 バイトすべてが描き替えた PNG と一致し、画面にも新しい文字が出て、
そのあとも BASIC は動き続けます。同じ日に `--chr-ram` のカートリッジ版でも確認しました。
起動した時点でキャラクタ RAM がダンプの絵と 8,192 バイト一致し、指定したタイルだけが
差し替わり、そのあと `BGGET` を実行してもルーチンは無事でした。

実物のファミコンでも確認しました（EverDrive N8 PRO に同じビルドを入れ、プログラムは
テープから読ませました）。画面の `O` がすべて指定した形になり、**数字の `0` は元のまま**
でした。似た形の 2 つのタイルのうち、描き替えた側だけが変わっています。

16KB 版のフリーエリアは `$8000` を越えます。そこはファミリーベーシックの数値が負になる
範囲（符号つき 16 ビット）なので、実際に測りました。`POKE &H9B00,123` は読み戻せ、
`I=5:POKE &H9B00+I,77` は `&H9B05` から読み戻せ、`CALL` は戻ってきます。
`CLEAR &H9AFF` は通り、そのあとの `FRE(0)` は `15094`（道具の計算どおりの値）。
`CLEAR &HA000` で機械は `?IL ERROR` を返します。

    $ ./tools/fb-pcg.py "Family BASIC V3 (Japan).nes" tiles.png -o pcg.bas \
          --top 0x9FFF --area 16374

⚠️ **`--top` に渡せるのは、`$9FFF` までで、かつページの切れ目で終わるフリーエリアです**
（最後の番地が `$xxFF` であること）。ページの切れ目なのは、ルーチンが 1 ページを
丸ごと使うからです。

## どのタイルがどのキャラクタか

`SPRITE(c, ...)` のキャラクタ番号は 0〜15 です。1 体は 2×2 の 4 枚で描かれ、
どの 4 枚を使うかの表が ROM の中にあります。`--map` はその表を、渡された ROM から読みます。

| c | タイル | | c | タイル |
|---|---|---|---|---|
| 0 | `$00-$0F`, `$14-$1B` | | 8 | `$98-$A3` |
| 1 | `$1C-$2B`, `$30-$37` | | 9 | `$A4-$AF` |
| 2 | `$38-$3F` | | 10 | `$B0-$B7` |
| 3 | `$40-$57` | | 11 | `$58-$5F` |
| 4 | `$60-$6F` | | 12 | `$D0`, `$D2`, `$D4`, `$EF` |
| 5 | `$70-$77` | | 13 | `$B8-$BF` |
| 6 | `$78-$8F` | | 14 | `$C0-$C7` |
| 7 | `$90-$97` | | 15 | `$C8-$CF` |

同じタイルを 2 体が使うことはありません。実際に描かれるタイル番号は

    タイル番号 = 表の 4 枚 + キャラクタごとの加算値 + 4 × アニメの駒数

です。アニメの次の駒は 4 枚先にあります。キャラクタごとの加算値だけが違って表を共有する
組み合わせがあり、キャラクタ 2・7・10・11・14 の 5 体は同じ 9 通りの表を
別々の加算値で読んだものです。

### 表の見つけ方と、そろっていない 2 か所

表は**番地ではなく形で**探します。16 個のポインタがあり、その先がそれぞれ 3 個のポインタ、
その真ん中が 9 個のポインタ（向き 1 つに 1 個）、その先が 4 枚のタイル番号。
この形をしている場所は ROM の中に 1 つしかありません。番地で探せないのは、
バージョンによって場所が動くからです（V3.0 は `$C709`、V1.0 と V2.x は `$BC75`）。

* **アニメの駒数の入れ方がバージョンで違います。** V1.0 と V2.x は 16 倍した値を持ち、
  反転の指定は別の表にあります。V3.0 は 1 バイトに詰めていて、下位 4 ビットが駒数、
  ビット 6 と 7 が反転です。数字そのものはどちらも同じです。読み方を間違えると、
  どのキャラクタもタイルが 1 枚も出てきません。
* **キャラクタ 0・1・4 には、表に載っていない 2 コマ目があります。** 向き 1 と 5
  （上り・下り）のとき、ROM はプログラムの中に書かれた 4 枚を指します。中身は 1 コマ目と
  同じ 4 枚を左右反転しただけなので、使うタイルは増えません。ただし、ほかの向きと同じに
  「4 枚先」と数えると、別のキャラクタのタイルを指してしまいます。実際、
  キャラクタ 4 がキャラクタ 5 に食い込みます。

どちらも決め打ちにしていません。読み方がずれたら必ず落ちる 2 つの条件で押さえています。
1 つは **16 体のタイルが重ならないこと**（コードが差し替える所で「4 枚先」と数えると、
キャラクタ 4 がキャラクタ 5 に食い込みます）。もう 1 つは
**どのダンプから読んでも同じ結果になること**です。バージョンが違えばプログラムの番地は
全部違うので、後者はそれ自体が答え合わせになります。

## 検査が何に立っているか

書き出して、戻して、ファイルを比べる。この往復検査では、**読みと書きで同じ間違いをしている
場合**を捕まえられません。1 タイルは 2 枚の面（bit plane）でできていて、この 2 枚を
取り違えて読み、取り違えて書けば、ファイルは 1 バイトも変わらないまま、
画面に見せていた絵だけが階調 1 と 2 が入れ替わったものになります。

そこで階調の意味は、別の人が書いた資料に合わせてあります。NESdev Wiki のパターンテーブルの
ページ（<https://www.nesdev.org/wiki/PPU_pattern_tables>）に、16 バイトと、それが描く 8 行の
階調が載っています。検査は毎回このバイト列を復号して比べ、さらに符号化して戻します。
実際にこの検査が効いているかは、面を読み・書きの両方で入れ替えてみて落ちることで
確かめてあります。往復検査はここを見逃します。
