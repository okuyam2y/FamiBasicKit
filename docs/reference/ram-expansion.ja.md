# プログラム領域を広げる — 書き換える箇所

*ビルドを改造する人のための文書です。どこを書き換えるのか、なぜそれで足りるのかを
説明します。使うだけなら[使い方](../manual/building.ja.md)を読んでください。*

[English](ram-expansion.md)

## 1. 上限を決めているのは RAM の量ではありません

ファミリーベーシックは起動時に、プログラム領域の最後のアドレスをゼロページの
`$03/$04` に格納します。この値は ROM に書かれた即値なので、ハードウェアが実際に
どれだけ RAM を用意していても結果は変わりません。

空き容量の表示はこの 2 バイトから計算されます。ここを書き換えると領域が広がります。
ただし、これだけでは足りません。`CLEAR` が受け付ける上限が別の定数になっており、
V3 では `BGGET`/`BGPUT` が使うバッファの位置も別の定数です。それぞれ個別に変更する
必要があります。

書き換える箇所は 3 つです。

1. 起動時の初期化。ゼロページ `$03/$04` に入れる即値
2. `CLEAR` の引数チェック。「このアドレス以上ならエラー」という判定の即値
3. `BGGET`/`BGPUT` のバッファ位置（V3 のみ）

⚠️ V1.0 だけは `$03/$04` を「最後のバイトの次のアドレス」として扱います（`$7800`）。
V2 と V3 は最後のバイトそのもののアドレスを入れます（`$77FF` / `$6FFF`）。
判別は、直前に `LDA #$FF / STA $03` があるかどうかで行います。
`fb-expand-basic-area.py` は自動で判別します。

| バージョン | 標準の領域 | 拡張後 |
|---|---|---|
| V1.0 / V2.0A / V2.1A | `$7000-$77FF`（2KB） | `$7000-$7FFF`（4KB） |
| V3.0 | `$6000-$6FFF`（4KB） | `$6000-$7FFF`（8KB） |

上限がバージョンによって違うのは、領域の先頭が違う位置にあるためです。V1/V2 は `$7000` から
始まるため、先頭を動かさずに `$7FFF` まで伸ばすと 4KB になります。V3 は `$6000` から
始まるため 8KB まで届きます。

### ヘッダも 1 バイト変更します

PRG を書き換えても、ハードウェアが RAM を用意しなければ意味がありません。
NES 2.0 ヘッダのバイト 10 の上位ニブルが NVRAM のサイズを表します
（`5`＝2KB、`6`＝4KB、`7`＝8KB、`8`＝16KB）。

| 変更 | ヘッダのバイト 10 |
|---|---|
| V1/V2 → 4KB | `$50` → `$60` |
| V3 → 8KB | `$60` → `$70` |

変更量の合計は、V3 で PRG 5 バイトとヘッダ 1 バイト、V1/V2 で PRG 2 バイトとヘッダ
1 バイトです（V1/V2 には `BGGET` がないためです）。

`fb-expand-basic-area.py` はこれらをまとめて書き換えます。`--keep-header` を指定すると
ヘッダを変更しませんが、そのROM は実機で効果がありません。

### `BGGET`/`BGPUT` のバッファはプログラム領域の末尾に置かれます

`BGGET` は背景画面を RAM に保存し、`BGPUT` は書き戻します。この 2 命令が共有する
1KB のバッファの位置は、次の 3 つの即値（バッファの上位バイト）で決まります。
下位バイトはいずれも `$00` です。

| アドレス | 命令 | 役割 |
|---|---|---|
| `$B1BD` | `CMP #>buf` | `BGGET`：プログラムの上にバッファを置く余地があるかの判定 |
| `$B1CA` | `LDA #>buf` | `BGGET`：画面の保存先 |
| `$B20B` | `LDA #>buf` | `BGPUT`：書き戻すときの読み出し元 |

未改造の V3 ではここが `$6C` なので、バッファは `$6C00-$6FFF` になります。
標準の領域 `$6000-$6FFF` の最後の 1KB です。

領域を広げてもこの 3 か所を変更しなければバッファは移動しません。その結果、
バッファがユーザーのプログラムの内部に位置することになり、`$B1BD` の判定が
プログラムのサイズが `$6C00` を超えた時点で `?OM ERROR` を返します。実際にはまだ
空きがあっても止まります。

これは 2026-08-23 まで実際に発生していた不具合です。実機では、16KB 版で 3,529 バイトの
プログラムを動かしたときに `12846 BYTES FREE` と表示された直後に `?OM ERROR IN 10` に
なりました。

そのため、バッファも領域に合わせて移動させます。8KB 版は `$7C00`、16KB 版は `$9C00` です。

⚠️ 参照はこの 3 か所だけです。2 つの逆アセンブラで独立に確認しています。
`fb-disasm.py` では、ベクタから到達できる命令の中に `#$6C` の即値がちょうど 3 つあり、
`$6C00-$6FFF` を指す 16 ビットの参照は 0 件でした。
[micahcowan/fbdasm](https://github.com/micahcowan/fbdasm) の注釈付き逆アセンブルでも
同じ 3 か所が該当します。

`$8007` と `$8009` にある `$6Cxx` は、内蔵プログラム 2 と 3 の終端アドレスです。
無関係なので変更してはいけません。

### ⚠️ 変更してはいけない箇所

V3 の `$ADC8` 付近にある、内蔵プログラムを ROM から領域へコピーするループの終了アドレスを
延ばしてはいけません。延ばすと転送元のポインタが ROM の末尾を超えて進み、アドレスの
折り返しによって副作用のあるレジスタ（PPU）に到達する可能性があります。

領域の末尾は `$03/$04` で管理されているため、このループを変更する必要はありません。

## 2. 8KB までは MMC5 が不要です

`$6000-$7FFF` の 8KB は、カートリッジが RAM を置く場所として元から用意されている範囲です。
マッパー 0（NROM）はバンク切り替え回路を持たないだけで、この範囲に実際の RAM を
置けないわけではありません。

実際のカートリッジが 2KB（V1/V2）や 4KB（V3）なのは、搭載された SRAM がそのサイズだった
ためです。残りはミラーになります。

- V2 の 2KB は 4 つのエイリアス（`$6000-$67FF` / `$6800-$6FFF` / `$7000-$77FF` / `$7800-$7FFF`）
- V3 の 4KB は 2 つのエイリアス（`$6000-$6FFF` / `$7000-$7FFF`）

したがって、ヘッダの宣言どおりに RAM を用意する環境であれば、マッパー 0 のままで 8KB まで
届きます。逆に、無改造のカートリッジでは拡張しても意味がありません。エイリアスによって
同じ記憶素子に折り返すためです。

| 目的 | 必要な変更 |
|---|---|
| V1/V2 を EverDrive で起動する | ヘッダを付けるだけ（ヘッダがないと `Unformatted ROM` になる） |
| V1.0 → 4KB | PRG 2 バイト ＋ ヘッダ 1 バイト |
| V2.1A → 4KB | PRG 2 バイト ＋ ヘッダ 1 バイト |
| V3 → 8KB | PRG 5 バイト ＋ ヘッダ 1 バイト |
| V3 → 16KB | MMC5（`$8000-$9FFF` にも RAM を割り当てる） |

⚠️ 空き容量の表示はプログラムを読み込んでいない状態の値です。`.sav` がある場合
（`BASIC HOT START`）はプログラムのサイズだけ減ります。比較するときは条件を揃えてください。

## 3. 16KB 版 — BASIC 本体の再配置

`$6000-$7FFF` の 8KB を使い切ると、残っているのは `$8000` 以降だけです。この範囲は本来
PRG-ROM なので、バンク切り替えのできるマッパー（MMC5）が必要になります。さらに、
`$8000-$9FFF` に置かれている BASIC 本体 8KB の置き場所がなくなります。

空けられる場所は、内蔵プログラム 4 本（音楽デモとゲーム 3 本）がある `$D400-$FFF9` だけです。
そこで BASIC 本体をここへ移し、内蔵プログラムはバンクへ移します。

⚠️ 8KB と 16KB の中間はありません。RAM は 8KB 単位で割り当てるため、12KB という選択肢は
存在しません。

### 電源投入後のメモリ配置

| CPU アドレス | 内容 |
|---|---|
| `$6000-$7FFF` | WRAM ブロック 0（フリーエリアの下半分） |
| `$8000-$9FFF` | WRAM の 2 つめのブロック（上半分。バンク番号は起動時に判定 → [mmc5-wram-banks.ja.md](mmc5-wram-banks.ja.md)） |
| `$A000-$BFFF` | ROM バンク 5（常駐。一部を書き換え済み。下記参照） |
| `$C000-$DFFF` | ROM バンク 6（元の `$C000-$CFFF` ＋ 移動した本体の前半） |
| `$E000-$FFFF` | ROM バンク 7（本体の後半、タイトル画面、初期化、ローダ、ベクタ） |
| バンク 0-3 | 内蔵プログラム 1 本ずつ（下半分は `$C000-$CFFF` の複製） |

#### バンク 5 に入れている変更

バンク 5 は、再配置で移動しない側の本体です。アドレスは元のままですが、元の ROM の
そのままのコピーではありません。ここへの書き込みはすべて `fb-mmc5-16k.py` の `put_a()` を
通しており、置き換える対象のバイトが想定どおりでなければ処理を中止します。

| 書き込み先 | 内容 | 理由 |
|---|---|---|
| `$AD96` | `GAME` の読み込み入口 | 作り直したローダへ向ける |
| `$ADD5` / `$ADF2` | タイトル画面のコピー元と終端 | 画像が `$D000` から移動したため |
| `$B1BE` / `$B1CB` / `$B20C` | `BGGET`/`BGPUT` のバッファのページ（`$B1BD` / `$B1CA` / `$B20B` の各命令のオペランド） | 広げた領域の末尾に合わせるため |

⚠️ 「バンク 5 は元の ROM と一致するはず」を検証の基準に使わないでください。
設計上一致しません。このビルド全体の検証は出力の MD5 で行います。

### `$5117` を書き込む必要はありません

MMC5 の `$5117` は電源投入時に `$FF`（ROM の最後のバンク）になります。初期化コードと
ベクタをその最後のバンク（バンク 7）に置いてあるため、電源投入直後から必要なものが
見えている状態になります。

これにより、MMC5 でよくある問題を回避できます。`$5117` に書き込んだ瞬間に、いま実行中の
コードが置かれているバンクが切り替わってしまう、という問題です。

### 内蔵プログラムの読み込み

内蔵プログラムはそれぞれ専用の 8KB バンクに置き、バンクの上半分（`$D000-$DFFF`）に
配置します。読み込みループは転送先が `$7000` に達するまで続き、転送量は最大 4,090 バイトです。
4,090 は 4,096 未満なので、バンクの終端を超えることはありません。バンクをまたぐ処理は
不要です。

各バンクの下半分は `$C000-$CFFF` の複製です。`$5116` は 8KB 単位で切り替えるため、
複製しておくことで、切り替え中に消えるのは `$D000-$DFFF` だけになります。

⚠️ 切り替えの間は NMI を禁止します。NMI ハンドラの本体（再配置後は `$D971`）が、
切り替えで消える `$D000-$DFFF` にあるためです。

⚠️ 再許可は `LDA $32 / ORA #$80 / STA $2000` で行います。`$32` は BASIC が持つ `$2000` の
控えですが、bit 7（NMI 許可）を保持していません。`LDA $32 / STA $2000` だけでは NMI が
禁止のままになり、画面もキーボードも停止します（実機で発生を確認しています）。

副次的な効果として、元の `GAME` にあった問題（ROM の末尾を超えて読み、`$0000` 方向へ
折り返して PPU や APU のレジスタに到達する）は 16KB 版では発生しません。処理がバンク内で
完結するためです。

### `.sav` は 32KB になります

16KB 版の `.sav` は 32KB で、8KB 版とは互換性がありません。ブロック 0 が `$6000-$7FFF`、
ブロック 1 が `$8000-$9FFF` に対応します。

MiSTer の NES コアでは、`prg_nvram != 7` の場合に `save_sz` が 32KB になるためです。
`./tools/fb-basic-to-sav.py -V v3 --16k` を使えばサイズは自動で決まります。

## 4. 再配置で修正した箇所と、その検証

`$8000-$9FFF` を別のアドレスへ移すと、そこを指している値をすべて修正する必要があります。
V3 では絶対アドレスの参照が 860 件あり、ほかに分岐表、即値 2 つで組み立てたアドレス、
ベクタがあります。

ROM のうち静的に到達できるのは一部だけです。そのため「`$80xx-$9Fxx` に見えるバイトの
並びをアドレスとみなす」方法ではデータを破壊します。

`fb-relocate.py` は入力が未改造の V3 でなければ動作しません（PRG+CHR の SHA-256、
3 本のベクタ、未定義オペコードの位置、コード断片の入口を照合します）。
また、実際に修正した件数を毎回出力します。

件数の内訳、実際に発生した問題、結果の検証に使った 3 つの方法は
[relocation-notes.ja.md](../background/relocation-notes.ja.md) にあります。
