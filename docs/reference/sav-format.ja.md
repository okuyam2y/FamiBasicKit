# BASIC プログラムの格納形式

*ビルドを改造する人、または `.sav` を読み書きするツールを書く人のための文書です。
プログラムを本体に入れたいだけなら[使い方](../manual/building.ja.md)を読んでください。*

[English](sav-format.md)

`tools/fb-basic-to-sav.py` が実装している形式です。全体の検証は往復で行っています。
ROM 内蔵のプログラム 4 本（387 行・8,999 バイト）を復号してから再変換し、1 バイトも
違わないことを求めます（`--selftest`）。

## バージョンによって配置が異なります

| | V1.0 / V2.0A / V2.1A | V3.0 |
|---|---|---|
| 領域の先頭 | `$7000` | `$6000` |
| プログラム本体 | `$703E`（オフセット `0x103E`） | `$6006`（オフセット `0x0006`） |
| 起動時の署名 | `$703A`＝`$5A` / `$703B`＝`$33` | `$6001`＝`$4C` |
| プログラムの終端ポインタ | `$703C/$703D` | `$6002/$6003` |
| 領域の末尾 | `$77FF`（拡張時は `$7FFF`） | `$6FFF`（拡張時は `$7FFF`） |

⚠️ 署名と終端ポインタの両方が必要です。署名だけでは「カセットにデータがある」ところまでで、
終端ポインタがないとプログラムは空として扱われ、`LIST` に何も表示されません。

### V2 系の復元経路（`$80FB` から）

```
80D7  LDA #$5A / STA $703A     ; 保存側
80DC  LDA #$33 / STA $703B
80E3  LDA $07  / STA $703C     ; プログラムの終端（下位）
80E8  LDA $08  / STA $703D     ;                （上位）

80FB  LDA $703A / CMP #$5A     ; 復元側（タイトル画面でキーを押すと実行される）
8102  LDA $703B / CMP #$33
8109  LDA $703C → $07 / LDA $703D → $08
8113  LDA #$3E / LDA #$70 → $05/$06   ; 領域の先頭 $703E
```

⚠️ `$CF5B` にある `CMP #$CC` は別の経路です。これを見て「署名は `$CC`」と判断すると、
`LIST` が空になる原因を延々と探すことになります。

### V3 のヘッダ（`$812B` の判定）

| アドレス | `.sav` のオフセット | 意味 |
|---|---|---|
| `$6001` | `0x0001` | 署名 `$4C`。これ以外の値ならプログラムは破棄されます（`$812E` の `CMP #$4C`） |
| `$6002`/`$6003` | `0x0002` | プログラムの終端アドレス（終端の `00` の次） |
| `$6004` | `0x0004` | 起動時にゼロページ `$7C` へコピーされます（用途は未調査。`$00` で動作します） |
| `$6006` | `0x0006` | プログラム本体の先頭（`$05/$06` に `$6006` が入ります） |

## 行の格納形式

```
行 = [長さ 1B（自身を含む）][行番号 2B LE][本体...][00]
本体 = トークン（$80 以上）／生の ASCII／数値／文字列（引用符も生のまま）
最後の行の後ろに 00 を置き、終端ポインタはその次のバイトを指す
```

終端ポインタより後ろの内容は規定されていません。`.sav` は固定サイズの RAM イメージなので、
通常はプログラムの後ろに余りが残ります。BASIC はそこを読みません。プログラムがどこで
終わるかは終端ポインタが示すためです。

プログラムが領域をちょうど埋めた場合は、終端の後ろに何も残りません。どちらの場合も
特別な扱いはありません。実機が書いた `.sav` では、この部分に `0x20` が入っている例を
確認しています。`fb-basic-to-sav.py` は新規作成時にゼロを書き、`--base` を指定した場合は
元の内容を残します。

この文書は以前、`0x20` で埋めることを形式の一部として記載していましたが、そのように
出力するツールはなく、必要としているものもありません。

### 数値の表現は 3 種類と、もう 1 つ

以前の実装はすべてが `$12` だと想定していました。そのため `GOTO` や `GOSUB` を含む
プログラムは必ず `?SN ERROR` になっていました。

| 形式 | バイト | 内容 |
|---|---|---|
| 1 桁の整数 | `$01`-`$0A` | 0-9（値＋1。`$00` は行の終端なのでずらしてあります） |
| 整数 | `$12 lo hi` | 10 以上 |
| 16 進数 | `$11 lo hi` | `&Hxxxx` と書いたもの |
| 行番号 | `$0B lo hi` | `GOTO`/`GOSUB`/`THEN`/`RESUME`/`RESTORE` の後ろ、およびそれに続く `,` の後ろ |

⚠️ 1 桁の短い形式は V3 のみです。V2 系は 0-9 も `$12 lo hi` で表します。

⚠️ `REM` と `DATA` の後ろは行末まで生のまま格納されます。トークン化も数値への変換も
行いません。`DATA 11,22` を数値トークンにすると、`READ` が `?TM ERROR` になります。

例：`10 POKE 24576,65` → `0d 0a 00 9e 20 12 00 60 2c 12 41 00 00`

文字列は引用符を含めて生の ASCII です。1 バイトのトークンになるのは予約語だけで、
`,` `(` `)` は生の ASCII のまま残ります。

### 予約語の表はバージョンで異なります

V3 は 109 語（`$CCAB-$CEBE`）、V2 系は 88 語（`$C128-$C2C5`）です。どちらの範囲も
表の終端を示す `$FF` を含み、いずれも ROM から実測しました。

この文書には以前 `$C120-$C2BF` と `$CCAB-$CEBD` と書かれており、同じ表についてツールが
報告する値と食い違っていました。アドレスは文書ではなく ROM から取るべきで、
`fb-basic-to-sav.py` はそうしています。

V3 が追加している 21 語は次のとおりです。

`TR` `FIND` `GAME` `BGTOOL` `AUTO` `DELETE` `RENUM` `FILTER` `CLICK` `SCREEN` `BACKUP`
`ERROR` `RESUME` `BGPUT` `BGGET` `CAN` `INSTR` `CRASH` `ERR` `ERL` `VCT`

この文書は以前 87 語・22 語と記載し、追加分に `SCR$` を含めていました。実際には
V2.1A にも `SCR$` があり、番号は `$E1` で V3 と同じです（両方の ROM から数えました）。
手書きの一覧から `SCR$` が抜け落ちたことが過去に一度あり、ツールが一覧を持たずに
ROM から読み直しているのはそのためです。

⚠️ V3 に V2 の表を使うと、追加された語がすべて 1 文字ずつの ASCII になります。
表の形式は「トークン値（bit 7 が 1）に続けて語を ASCII で置く」の繰り返しなので、
ROM から読み直せます。

⚠️ `TAB` / `SPC` / `COLOR` は予約語ですが、命令としては実装されていません。
V3 のマニュアルには「将来の拡張用に予約されているため、変数名には使えない」とあります。
実機で実行すると `?SN ERROR` になります。

## 自己検証

```bash
./tools/fb-basic-to-sav.py --selftest "Family BASIC V3 (Japan).nes"
```

内蔵プログラム 4 本を復号してから再変換し、1 バイトも違わないことを求めます。
予約語の表は ROM から読み直して照合します。目的は、正解の基準を実装者の理解の外に
置くことです（解釈できずにそのまま通したバイトは 2.2% です）。

## 補足

`POKE`（`$9E`）、`PEEK`（`$CF`）、`CALL`（`$AD`）は標準で使えます。
領域を拡張しなくても、BASIC が使っていない WRAM に `POKE`/`PEEK` で読み書きできます。

```basic
POKE 24576,65 : PRINT PEEK(24576)   ' $6000 に書いて読むと 65 が返る
```
