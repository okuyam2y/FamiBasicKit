# 8KB のコードを別のアドレスへ移すときに問題になった点

*背景の記録です。再配置の処理がこの形になっている理由と、途中で発生した問題を
記録しています。ビルドを使うにも、命令を追加するにも必要ありません。*

[English](relocation-notes.md)

同じことを試す人のための記録です。複数のモデルによるレビューで、実機で動作していた
ROM から実際の不具合が 2 件見つかりました。どちらも出力は正しく見え、静的な検査を
すべて通り、通常の使用では再現しませんでした。

## 1. 「まとめて移せば内部は保たれる」が成り立たない場合が 2 つあります

相対分岐をそのままにしてよいのは、分岐先が移動する範囲の内側にある場合だけです。

### 範囲の外へ出る相対分岐（3 件）

V3 の ROM には、移動する範囲の終端付近に、範囲の外へ分岐する命令が 3 つあります
（`$9FE1` / `$9FF9` / `$9FFD` から `$A005` / `$A009` へ）。移動すると、これらは
まったく別のコードを指すようになります。移動先は MMC5 の初期化ルーチンの先頭と、
命令の途中でした。

対処は、移動する範囲を分岐先まで広げることです。広げると新しい分岐が範囲に入るため、
新しく出てこなくなるまで繰り返します。結果として範囲は `$8000-$A001` ではなく
`$8000-$A00A` になりました（中継部分は `$F00B-$F00D` にあります）。

つまり、移動する範囲は固定値ではありません。`fb-mmc5-16k.py` はこの値を持たず、
`fb-relocate.py` が再計算した値と照合します。以前の実装はこの値を持っていました。
その状態で本体が大きくなったときに検査が通ってしまい、初期化コードが本体を
上書きしました。

### 命令の重なり（1 件）

`BIT abs`（`2C lo hi`）がオペランドの 2 バイトを取り込む形になっていて、その 2 バイト目へ
分岐すると、同じ 2 バイトが別の命令として実行される、という書き方があります。

V3 では `$9642` の `BIT $9785`（`2C 85 97`）がこれにあたります。`$9643` へ分岐すると、
同じ 2 バイトが `STA $97` として実行されます。このオペランドはアドレスであると同時に
命令でもあるため、アドレスとして書き換えてはいけません。書き換えると `STA $E7` になり、
分岐してきた経路が別の変数を破壊します。

ROM 全体では重なりが 16 件あり、そのうち 1 件が問題になりました。

移動する前に、次の 2 つを数えてください。

- (a) 範囲内の相対分岐のうち、分岐先が範囲外にあるもの
- (b) オペランドのバイトが、別の命令の先頭バイトでもあるもの

どちらも 0 であれば、その範囲は単独で移動できます。0 でなければ、範囲を広げるか、
その参照を書き換え対象から除外します。

静的な検査でこれらを見つけられない理由は、どちらの場合も参照の値と命令の境界が
すべて想定どおりに出てくるためです。

（可変長で、命令の途中から実行を始められる命令セットに当てはまります。6502 と x86 が
該当します。ARM64 のように固定長でアライメントを要求する命令セットでは (b) は起きません。）

## 2. バイト列の一致は仮説であって、意味ではありません

バイナリを検索して見つかった並びは、何かに見えるバイトの並びであって、そのコードが
何をしているかの証拠ではありません。書き換える前に周辺を読んでください。

実例があります。「領域の末尾との比較に見える」パターン（`LDA #$70 / CMP / BNE`）に
3 か所が一致し、そのうち 1 か所を書き換えました。逆アセンブルして読んだところ、
これは範囲チェックではなく、ROM から領域へデータをコピーするループの終了条件でした。
終端を延ばしたことで転送元のポインタが ROM の末尾を超えて進み、アドレスの折り返しで
副作用のあるレジスタ（PPU）に到達する可能性がありました。

手順は、候補を見つけたら、そのアドレスの周辺を逆アセンブルして読み、コードが何をしているかを
言葉で説明できるようになってから書き換える、という順序です。言葉にできない場合は
書き換えないでください。

`tools/fb-disasm.py` はこのためのツールです。`RESET` / `NMI` / `IRQ` から再帰的に
たどり、ベクタから実際に到達できる命令だけを命令として扱います。到達できなかった範囲は
「データ」ではなく「未確認」として報告します。

## 3. 分岐表とデータ表の区別

`$80xx-$9Fxx` に見える 16 ビットの値が、すべて移動の対象になるアドレスとは限りません。
判断は、その表を読んでいる命令で行います。

分岐表は間接 `JMP` に渡す形をしています。

```
LDA 表,X / STA $19 / LDA 表+1,X / STA $1A / JMP ($0019)
```

V3 で変更してはいけないデータ表は次のとおりです。値がたまたま `$80xx-$9Fxx` に
見えるだけです。

| アドレス | 内容 |
|---|---|
| `$8013` | 音程のデータ |
| `$B37F` | パレット |
| `$B44A` | ファンクションキーの文字列 |
| `$C787` | 16 ビットの加算値 |

`fb-disasm.py` の `--find-tables` は、全項目が ROM 内のアドレスになっている並びを
候補として挙げるだけです。判断は、後続の命令を読んで行います。

## 4. 修正した参照の件数（V3 での実測）

| 種類 | 件数 | 見つけ方 |
|---|---|---|
| 絶対アドレスの `JSR`/`JMP`/データ参照 | 860 | 逆アセンブルした命令のオペランド |
| 相対分岐 | 479 | 変更しない（分岐先も移動するよう範囲を広げてある） |
| 分岐表の項目 | 4 表 | 上記の形 |
| 即値 2 つで組み立てたアドレス | 2 | `LDA #<lo / STA zp / LDA #>hi / STA zp+1` |
| リセット／IRQ ベクタ | 2 | `$FFFC` / `$FFFE` |

この表は考え方を説明するためのものです。判断の根拠にしているのは実行時の出力で、
`fb-relocate.py` は実際に修正した件数を毎回出力します。

## 5. 検査の書き方

- 「何か所変わったか」ではなく「意図した場所が変わったか」を検査してください。
  件数による検査は、同じ件数だけ別の場所を壊したときにも同様に通ります
- 検査する側に期待する答えを渡さないでください。渡すと、定数が間違っていた場合に
  検査も同じ方向に間違い、そのまま通ります
  （[mmc5-wram-banks.ja.md](../reference/mmc5-wram-banks.ja.md) のバンク番号の判定）
- 入力を固定してください。`fb-relocate.py` は入力が未改造の V3 でなければ動作しません
  （PRG+CHR の SHA-256、3 本のベクタ、未定義オペコードの位置、コード断片の入口）
- 「動いた」ではなく「未改造の ROM と同じ画面になる」を検査してください。
  再配置の不具合は、めったに通らない経路が静かに壊れる形で現れます

## 6. 結果の検証方法

エラーが出ないことは検証ではありません。ここでは 3 つの方法を使いました。

- `fb-mmc5-16k.py` に組み込んだモデル実行。6502 と MMC5 のバンク切り替えを最小限に
  模したもので、生成した起動時の判定コードを実際に実行します（`WRAM_MODELS`）。
  バンク番号の解釈を `linear` / `chip` / `only8k` と切り替えて、それぞれの結果を出力します。
  `$5114-$5116` の電源投入時の値は未定義なので、未設定の状態を無効値として扱い、
  設定前に `$8000-$DFFF` を参照した時点で停止します
- `fb-basic-to-sav.py --selftest`。内蔵プログラム 4 本（387 行・8,999 バイト）を
  復号してから再変換し、1 バイトも違わないことを求めます。目的は、正解の基準を
  実装者の理解の外に置くことです
- 未改造の ROM との画面比較。再配置の不具合は、めったに通らない経路が静かに壊れる形で
  現れます。そのため検査は「動いた」ではなく「未改造の V3 と同じ画面になる」です。
  `tests/basic/` がこの用途のものです。未改造の V3 は 4KB しか空きがないため、
  それより大きいプログラムは `fb-gen-bigtest.py` で検査します。答えを別に計算できる
  プログラムを生成するツールです

この方法には効果がありました。実機で既に動作していた ROM から、複数モデルによるレビューで
実際の不具合が 2 件見つかっています。どちらも出力は正しく見え、静的な検査をすべて通り、
通常の使用では再現しませんでした。この文書の冒頭に挙げた 2 件です。
