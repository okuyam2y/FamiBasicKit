# プログラム領域はどこまで伸ばせるか

*背景の記録です。このプロジェクトが 16KB で止まっている理由と、次の一段の値段。
版を使うにも、改造するにも、ここは要りません — 天井の裏にある割り算で、
**実測した数字を先に置き、推測は推測と明示**しています。*

[English](area-ceiling.md)

## すべての天井の裏にある規則

プログラム領域は**連続した1本**で、BASIC は最後のバイトの番地を `$03/$04` に、
プログラムの終端を `$07/$08` に持ちます。**普通の16ビットポインタ**で、バンクの概念はありません。

**どこから始まるかは版によります**: V3 は `$6000`、V1/V2.0A/V2.1A は `$7000`
（[sav-format.ja.md](../reference/sav-format.ja.md)）。以下の数字は断りが無ければ V3 のものです。ディスク版は
V2.1A の領域を `$6000` へ降ろしているので、結果として両方が同じ範囲になります。

∴ **本体の途中に空きがあっても、プログラム領域は1バイトも増えません。** 数に入るのは
いま領域が終わっている場所の**すぐ上**だけです。

これは理屈ではありません。ディスク版は `$C5A1` に 1,522 バイトの死んだ台詞を見つけましたが、
空き容量の表示は1バイトも動きませんでした。そこは `SAVE`/`LOAD` の置き場になりました。

## V3 の ROM に何が入っているか

V3 の注釈付き逆アセンブル [micahcowan/fbdasm](https://github.com/micahcowan/fbdasm) の
ラベル表から。番地は手元のダンプと照合済みで、両者の差は iNES ヘッダ16バイトだけ、
本体は1バイトも違いません。

| | | |
|---|---|---|
| `$8000-$BDCD` | 本体・エディタ・キー入力・音・PPU | |
| `$BDCE-$BFCD` | カセット転送（低レベル） | 512 |
| `$BFCE-$C708` | `BGTOOL`（グラフィックエディタ） | 1,851 |
| `$C709-$CCAA` | スプライトの表・`CRASH`・`CAN` | 1,442 |
| `$CCAB-$CEBE` | `tbl_KeywordTokens`（予約語表） | 532 |
| `$CEBF-$CF7A` | `jtbl_Commands` / `jtbl_Functions`（分岐表） | 188 |
| `$CF7B-$CFFF` | 著作権表示・パレット表 | 133 |
| `$D000-$D3FF` | `gameBackgroundMap`（内蔵プログラム用の背景） | 1,024 |
| `$D400-$FFF9` | `txtGame0`〜`txtGame3`（内蔵プログラム4本） | |
| `$FFFA-$FFFF` | ベクタ | 6 |

`SAVE`/`LOAD` の命令側は別の場所です: `$9D44-$9EC8` の 389 バイト。

## 本体が要るのは 20,480 バイト

`$8000-$CFFF`。内蔵プログラムとその背景マップ（`$D000` 以降）は**除いています** —
MMC5 は専用のバンクへ追い出しており、ディスク版には用がないからです。

**20,480 ＝ 8KB × 2.5。** カートリッジは RAM を 8KB の窓単位でしか割り当てられないので、
**この1つの事実が以下の全部を決めます。**

## カートリッジでの割り算

`$6000-$FFFF` は 8KB の窓が5つです。

| プログラム領域 | 本体に残る窓 | 本体が要る量 | |
|---|---|---|---|
| 8KB | 4つ（32,768） | 20,480 | ✅ |
| **16KB** | **3つ（24,576）** | 20,480 | ✅ **4,096 余る — いまここ** |
| 24KB | 2つ（16,384） | 20,480 | ❌ **4,096 不足** |
| 32KB | 1つ（8,192） | 20,480 | ❌ |

本体は 2.5 窓ぶんなので、3窓を占めます。5 − 3 ＝ 2 窓＝ **16KB。3つ目の窓に余っている
4,096 バイトが、そもそも収まっている理由**です。プログラムに3つ目の窓を渡すには、
本体が2窓に収まる必要があり、**ちょうど 4,096 バイト減らす**ことになります。

## その 4,096 バイトの値段

| 消すもの | 番地 | バイト | 失うもの |
|---|---|---|---|
| `BGTOOL` | `$BFCE-$C708` | 1,851 | グラフィックエディタ |
| カセット（低レベル） | `$BDCE-$BFCD` | 512 | |
| `SAVE`/`LOAD` の命令側 | `$9D44-$9EC8` | 389 | テープへの保存そのもの |
| 文字列・パレット表 | `$CF7B-$CFFF` | 133 | 起動時の表示・`CGSET` の既定色 |
| **小計** | | **2,885** | **1,211 不足** |
| スプライトの表・`CRASH`・`CAN` | `$C709-$CCAA` | 1,442 | **`SPRITE` `MOVE` `POSITION` `CUT` `ERA` `CRASH` `CAN`** |
| **合計** | | **4,327** | 231 余る |

∴ **上で特定できている塊の中では、最後の 1,211 バイトは `SPRITE` でしか払えません。**
これは2つのことを言っていません。**ほかに 1,211 バイトが無いことの証明ではありません** —
V3 自身の死に領域は一度も測っておらず、健全に測れる道具は V2.1A に固定されています
（下の「確認できていないこと」）。そして動くキャラクタの無いファミリーベーシックに価値が
あるかは、測定ではなく判断の問題です。

実際にやる場合の作法を2つ:

- **命令語は消せません。消せるのは実装だけです。** [token-numbering.ja.md](../reference/token-numbering.ja.md) の規則1が
  番号を凍結しているので、`$B4` はどこかへ飛ぶ必要があります。**ディスク版はまさにこれを
  やっています**: トークン `$B3` は分岐表に残って `$AD5B` を指したままで、`$AD5B` の中身を
  `LDA #$01 / JMP $B237` に差し替えました。∴ 打たれると `?SN ERROR` が出て、消したコードは
  走りません。（同じ版にある**潰した台詞の索引を `?MSG` へ向け直す**歯止めは別物で、
  ルーチンが上書きしたデータの話であってトークンの凍結とは関係ありません。ここで前例として
  挙げていたのは誤りでした — レビューで判明）
- **消すことは詰めることです。** 穴より上が全部ずれるので、`fb-relocate.py` と同じ種類の
  作業になります（V3 で直した参照は 860 箇所）

## バンクへ追い出しても楽になりません

内蔵プログラムと同じように `BGTOOL` を差し替えバンクへ出す案は、技法ではなく**割り算**で
止まります。**切り替え窓そのものが、同じ 16,384 バイトから面積を食う**からです。
X バイトを追い出し、窓の大きさを S とすると:

```
(20,480 − X) + S = 16,384      ∴  X = 4,096 + S
```

一番大きな住人は `BGTOOL` の 1,851 なので `S ≥ 1,851`、∴ `X ≥ 5,947`。バンクへ出せると
分かっているものの合計は **4,194**（1,851 ＋ 1,442 ＋ 512 ＋ 389。削除の表にある文字列・
パレット表 133 はここでは除外 — BASIC がどこからでも読むので、出たり入ったりする窓には
置けない）で足りません。**追い出すほど、追い出すための窓も要ります。**
素直に消す（4,096）方が安く付きます。

⚠️ 以前の版は 4,155 と書いていました。カセット命令側の古い数字（350。上の表では 389）を
使っていたためです。どちらでも 5,947 には届かないので結論は動きません
（レビューで判明）。

内蔵プログラムが簡単だったのは、あれが**データ**で、写すループ1つ（`$ADB8`）で読まれるからです。
`BGTOOL` は対話するコードで、しかも自己完結していません — 自分のルーチンの1つ
`BgtFile_GoToScreen0` が塊の外（`$AE96`）にあります。

## ディスク版は、同じ壁に1窓ぶん低いところで当たります

RAM アダプタは `$6000-$DFFF` の 32,768 バイトを平坦に持ち、擬似ベクタが `$DFF6-$DFFF` に
固定されます。窓が無いので本体はどこからでも始められます。

以下の数字はすべて実測か、実測からの引き算です。**答えではなく引き算を見せます。** 入力:

| | バイト | 出どころ |
|---|---|---|
| RAM `$6000-$DFFF` | 32,768 | NESdev wiki [Family Computer Disk System](https://www.nesdev.org/wiki/Family_Computer_Disk_System) |
| 擬似ベクタ `$DFF6-$DFFF` | 10 | 同上。固定で動かせない |
| V3 の本体 `$8000-$CFFF` | 20,480 | 上記のラベル表 |
| ディスク版自身の `SAVE`/`LOAD` | 384 | `tools/fb-fds.py` の `SAVE_SIZE` |
| その起動ルーチンと IRQ スタブ | 88 | 同 `V3_FDS_INIT` ＋ `RTI` 1 バイト |

```
32,768 − 10 = 32,758   使える範囲 $6000-$DFF5
20,480 + 384 + 88 = 20,952   利用者のプログラム以外の全部
32,758 − 20,952 = 11,806   プログラム領域 $6000-$8E1D
```

⚠️ **この開始をページ境界へ切り上げると成立しません**。本体が `$9000-$DFF5` になり、
20,480 バイト要るものに 20,470 しか無いからです。**10 バイト足りません** — 本体を半端な番地から
始めるか、10 バイトをどこかから持ってくるかになります。（この文書の前の版は切り上げた上に
`$6000-$8FFF` を丸ごと空きに数え、しかもディスク版自身の 472 バイトを勘定から落としていました。
レビューで判明）

16KB にするなら本体は `$A000-$DFF5` ＝ 16,374 に収まる必要があり、20,952 に対して
**4,578 不足**です。

⚠️ これは V3 の数字で、しかも**まだ誰も作っていない版**の話です。`fb-fds.py` は V2.1A と V3 の
どちらからでもディスクを組めますが、**どちらも本体をカセットの位置に置いたまま** `$6000-$7FFF`
を取ります（V2.1A で `8126 BYTES FREE`・V3 で `8182`）。上の 11,806 に届かせるには本体を丸ごと
上へ詰める必要があり、いまのどちらの版がやっていることとも別の作業です。

その作業は V2.1A の方が厄介です。あちらの本体は `$8000-$DFFF` を埋め尽くし、`$E000` 以降を
11 箇所参照しています（V3 は 0 箇所）。実測できている死に領域は 1,522 バイトの台詞の塊だけで、
しかも真ん中にあるので何も買えません。

∴ **ディスクは見かけほど広い媒体ではありません。** カートリッジは本体を ROM に置けますが、
ディスクシステムには置く ROM が無いので、本体とプログラムが同じ 32KB を分け合います。

## マシン語（細切れ可）では、希少な資源が入れ替わります

マシン語は連続した1本を必要としないので、天井が番地の話でなくなります。
現行の 16KB 版を実測すると:

| | バイト | |
|---|---|---|
| **バンク4** | **8,192** | 全部 `$FF`。どこにも割り当てられていない。`$5116` で `$C000-$DFFF` へ差し替え |
| **バンク7 `$F553-$FFF9`** | **2,727** | **常駐**（`$E000-$FFFF` は切り替わらない）。内蔵プログラム4の残骸で、ローダはバンク3の複製から読むので死んでいる |
| フリーエリア | 16,374 | BASIC のプログラムと食い合う |

入口は安上がりです。`CALL` は `jsr FrmEval` / `jmp ($0400)` の2命令だけなので、
**飛び先は `$0400/$0401` ＝ `POKE` 2発**。NMI も最初から RAM トランポリン
（`$FFFA`→`$00ED`）なので、毎フレームのフックももう2発。

差し替えには作法が付きます。`GAME` のローダの流儀は、**差し替えるバンクの下半分に
`$C000-$CFFF` を複製**し、差し替え中は NMI を止めること。∴ 1バンクで使えるのは
**自己完結したコードなら 8,192 バイト**、**BASIC の `$C000-$CFFF` を下に残したいなら 4,096**。

∴ オーバーレイにすれば ROM 側はマッパーの容量まで伸びますが、**代わりに尽きるのは常駐部
——2,727 バイト**です。トランポリン・割り込みハンドラ・呼び出しの入口は、
切り替わらない場所にいる必要があります。

## 数の方が番地より先に止まる — しかも V3 の方が早い

実機で測りました（MiSTer・2026-08-25。各ディスクで4通りを1回の走行で打鍵）:

```
V2.1A:  PEEK(50976) → 0      PEEK(-14560) → 0    PEEK(32767) → 0    PEEK(50976) → 0
V3   :  PEEK(54655) → ?OV    PEEK(-10881) → 0    PEEK(32767) → 0    PEEK(50976) → ?OV
```

**同じ `50976` が V2.1A では通り V3 では溢れます。** ∴ 値の大小ではなく版の差です。
**V3 の整数リテラルは符号付き 16 ビット**（−32768〜32767）、V2.1A は 0〜65535 を受けます。
符号付きの形は両版で同じバイトに届くので、実機検定は版で打ち分けず
`PEEK(-10881)` を打ちます。

これが言っていること・言っていないこと:

- **打てる数の制限であって、届く番地の制限ではありません。** `POKE`/`PEEK` はどちらの版でも
  どこへでも届きます——番地を負の数で書くだけです。V3 で `$D57F` を触るプログラムは
  `PEEK(-10881)` と書きます。内蔵プログラムが同じ理由で別の綴りを使っています
  （`GAME 0` の `PEEK(&H4016)`。`&` はファミリーベーシックのキーボードにはあり、
  このプロジェクトの打鍵の道具には無い文字です）
- **空き容量の表示については、まだ何も言っていません。** あちらは別の経路です
  （下の「確認できていないこと」）

## 確認できていないこと

以下は全部、測定ではなく算術か推論です。**確かめる前にこの上へ何かを建てないこと。**

1. **MMC5 が 24KB の連続 WRAM を貼れるのかどうか。** [mmc5-wram-banks.ja.md](../reference/mmc5-wram-banks.ja.md) に
   取り込んであるのは `$5113`/`$5114`（`$6000-$7FFF` と `$8000-$9FFF`）までで、
   `$A000-$BFFF` を RAM にする側のレジスタは入っていません。⚠️ **ここは既に一度火傷している
   領域**です — 16KB 版はバンク番号の意味が実装ごとに違うせいで、起動時に**探る**必要がありました
2. **走行中に窓を RAM↔ROM へ倒せるかどうか。** できるなら、`BGTOOL` が動いている間だけ
   `$A000-$BFFF` をプログラム領域から借りて返せます。**何も消さずに 24KB 版が成立する**道です
3. **`FRE(0)` と `BYTES FREE` の表示が 32,767 を超えたときどうなるか。**
   このうち**リテラルの側は実測で片付きました**（上の節）。ただしあれはパーサの話で、
   バナーは別経路です——BASIC が値を計算して印字するので、リテラルは介在しません。
   負になるのか、回り込むのか、別の何かが出るのかは**まだ分かりません**。しかも
   **どちらの版でも答えを出せません**: ディスク版は約 11,806、16KB のカートリッジは 16,374 で、
   どちらも遠く届かないからです。答えを出すにはその数字に届く版が要り、それこそ
   この文書が「まだ作れない」と言っているものです。
   ⚠️ 以前の版はこの2つの上限を「1バイト差で並ぶ」と書いていました。`$6000-$DFFF` の
   32,768 を丸ごと数えた場合で、**FDS の節がベクタを引いている当の数字**です
   （レビューで判明）。16ビットの天井が効くのは、`$DFFF` より上にも
   RAM を貼る**カートリッジ**の設計の話です
4. **`$5116` を `CALL` から叩いたことはまだありません。** 差し替えの経路は `GAME` のローダが
   実証していますが、バンク4にコードを置いて走らせた人はまだいません。上の 10,919 バイトは
   「空だと実測した」段階で、「使えると実測した」段階ではありません
5. **V3 自身の死に領域は未測定です。** 健全に判定できるのは `tools/fb-reach.py` ですが、
   これは V2.1A の SHA-1 に固定されています。`fb-disasm.py --gaps` が返すのは**未到達**で、
   これは死んでいるという意味ではありません（分岐表で止まるため。`$C000-$DFFF` が到達率 0% と
   出るのに実際は生きたコードが入っているのがその例）

## 測り直し方

```bash
# 地図と、未到達の範囲
./tools/fb-disasm.py "Family BASIC V3 (Japan).nes" --gaps
./tools/fb-disasm.py "Family BASIC V3 (Japan).nes" --xref D400-DFFF

# トークン表（手書きの表ではなく ROM から読む）
./tools/fb-basic-to-sav.py --tokens "Family BASIC V3 (Japan).nes"
```

各塊の大きさは上記のラベル表から出しています —— そのラベルの番地と、
別のものに属する次のラベルの番地の差です。バンクの中身は組み上がった `.nes` から直接読みました
（バンク4は 8,192 バイトが全部 `$FF` で、それ以外の値は1つもありません）。

リテラルの範囲だけは、ダンプではなく**実機**から出た数字です。
**実機に打鍵する道具はこのリポジトリには入っていません** — 特定の MiSTer の接続設定に
結びついていて、それはまさに公開するリポジトリに置くべきでないものだからです。
再現するには、4通りの `PEEK` を各版に手で打つ（あるいはエミュレータで打つ）だけです。
答えは画面に出ます。
