# プログラム領域はどこまで広げられるか

*背景の記録です。このプロジェクトが 16KB で止まっている理由と、その次の段階にかかる
コストをまとめています。ビルドを使うにも改造するにも必要ありません。実測した数値を
先に置き、推測は推測として明示しています。*

[English](area-ceiling.md)

## 上限を決めている条件

プログラム領域は連続した 1 つの範囲です。BASIC は最後のバイトのアドレスを `$03/$04` に、
プログラムの終端を `$07/$08` に保持します。どちらも通常の 16 ビットポインタで、
バンクの概念はありません。

先頭がどこになるかはバージョンで決まります。V3 は `$6000`、V1/V2.0A/V2.1A は `$7000` です
（[sav-format.ja.md](../reference/sav-format.ja.md)）。以下の数値は、断りがなければ V3 の
ものです。ディスク版は V2.1A の先頭を `$6000` に移しており、そのため両方とも同じ範囲に
なります。

したがって、インタプリタの途中にある未使用領域は、プログラム領域の役には立ちません。
使えるのは、現在の領域の末尾に直接続いている空きだけです。

これは推測ではありません。ディスク版を作る際に `$C5A1` に 1,522 バイトの未使用の
メッセージ領域が見つかりましたが、空き容量の表示は 1 バイトも変わりませんでした。
この領域は `SAVE`/`LOAD` の置き場所になりました。

## V3 の ROM の内容

V3 の注釈付き逆アセンブル [micahcowan/fbdasm](https://github.com/micahcowan/fbdasm) の
ラベル表から求めました。アドレスは手元のダンプと照合済みです。両者の差は iNES ヘッダの
16 バイトだけで、本体は一致しています。

| 範囲 | 内容 | サイズ |
|---|---|---|
| `$8000-$BDCD` | インタプリタ、エディタ、キーボード、サウンド、PPU | |
| `$BDCE-$BFCD` | カセット転送の低レベル処理 | 512 |
| `$BFCE-$C708` | `BGTOOL`（グラフィックエディタ） | 1,851 |
| `$C709-$CCAA` | アクター／スプライトのテーブル、`CRASH`、`CAN` | 1,442 |
| `$CCAB-$CEBE` | `tbl_KeywordTokens`（予約語表） | 532 |
| `$CEBF-$CF7A` | `jtbl_Commands` / `jtbl_Functions` | 188 |
| `$CF7B-$CFFF` | 著作権表示の文字列、パレット | 133 |
| `$D000-$D3FF` | `gameBackgroundMap`（内蔵プログラム用） | 1,024 |
| `$D400-$FFF9` | `txtGame0`〜`txtGame3`（内蔵プログラム 4 本） | |
| `$FFFA-$FFFF` | ベクタ | 6 |

`SAVE`/`LOAD` の命令レベルの処理は別の場所にあります（`$9D44-$9EC8`・389 バイト）。

## 本体に必要なのは 20,480 バイト

`$8000-$CFFF` です。内蔵プログラムとその背景データ（`$D000` 以降）は含めていません。
MMC5 版はこれらを専用バンクに置き、ディスク版では使わないためです。

20,480 は 8KB の 2.5 倍です。カートリッジは RAM を 8KB 単位で割り当てるため、この数値が
以下のすべてを決めます。

## カートリッジでの計算

`$6000-$FFFF` は 8KB の窓 5 つ分です。

| プログラム領域 | 本体に残る窓 | 本体に必要 | |
|---|---|---|---|
| 8KB | 4 つ（32,768） | 20,480 | ✅ |
| 16KB | 3 つ（24,576） | 20,480 | ✅ 4,096 の余裕。現在のビルド |
| 24KB | 2 つ（16,384） | 20,480 | ❌ 4,096 不足 |
| 32KB | 1 つ（8,192） | 20,480 | ❌ |

本体には 2.5 窓分が必要なので、実際には 3 窓を占有します。5 から 3 を引いて 2 窓、
つまり 16KB です。3 つめの窓に 4,096 バイトの余裕があることで成立しています。

プログラム側に 3 つめの窓を渡すには、本体が 2 窓に収まる必要があります。つまり
ちょうど 4,096 バイトを削る必要があります。

## その 4,096 バイトの内訳

| 削るもの | 位置 | バイト | 失われる機能 |
|---|---|---|---|
| `BGTOOL` | `$BFCE-$C708` | 1,851 | グラフィックエディタ |
| カセット転送の低レベル処理 | `$BDCE-$BFCD` | 512 | |
| `SAVE`/`LOAD` の命令処理 | `$9D44-$9EC8` | 389 | テープへの保存全般 |
| 文字列、パレット | `$CF7B-$CFFF` | 133 | 起動時のバナー、`CGSET` の初期値 |
| 小計 | | 2,885 | 1,211 不足 |
| アクター／スプライトのテーブル、`CRASH`、`CAN` | `$C709-$CCAA` | 1,442 | `SPRITE` `MOVE` `POSITION` `CUT` `ERA` `CRASH` `CAN` |
| 合計 | | 4,327 | 231 の余裕 |

上に挙げた範囲の中では、最後の 1,211 バイトは `SPRITE` 関係を削る以外に確保できません。

ただし、これは 2 つのことを意味しません。1 つは、他に 1,211 バイトが存在しないことの
証明ではないという点です。V3 自体の未使用領域は測定していません。それを正しく測れる
ツールは V2.1A に固定されています（後述の「確認できていないこと」を参照）。もう 1 つは、
スプライトが動かないファミリーベーシックに価値があるかどうかは判断の問題であって、
測定の問題ではないという点です。

実行する場合の技術的な注意が 2 点あります。

- 命令語は削除できません。削除できるのはその実装だけです。
  [token-numbering.ja.md](../reference/token-numbering.ja.md) の規則 1 がすべての番号を
  固定しているため、`$B4` は何かを指し続ける必要があります。ディスク版が実際にこれを
  行っています。トークン `$B3` は分岐表に残り `$AD5B` を指したままで、`$AD5B` の内容を
  `LDA #$01 / JMP $B237` に置き換えてあります。そのため `GAME` を入力すると、削除した
  コードが実行されるのではなく `?SN ERROR` になります。
  （同じビルドには、上書きしたメッセージの番号を `?MSG` の目印に向ける処理も別にあります。
  そちらは処理が上書きしたデータについてのもので、固定されたトークンの話ではありません。
  ここで前例として挙げていたのは誤りでした。レビューで判明）
- 削除は同時に詰め直しでもあります。空いた場所より上にあるものはすべて下へ移動するため、
  `fb-relocate.py` と同じ種類の作業になります（V3 で 860 件の参照を修正しました）

## バンクへ追い出しても解決しません

内蔵プログラムと同じように `BGTOOL` を切り替えバンクへ移す方法は、技術ではなく計算で
行き詰まります。切り替え用の窓が、同じ 16,384 バイトからアドレス空間を消費するためです。
追い出すバイト数を `X`、窓のサイズを `S` とすると次のようになります。

```
(20,480 − X) + S = 16,384      X = 4,096 + S
```

`BGTOOL` が最大の 1,851 バイトなので `S ≥ 1,851`、したがって `X ≥ 5,947` です。
これに対して、バンクへ移せると分かっている範囲の合計は 4,194 バイトです
（1,851＋1,442＋512＋389。上の表にある文字列とパレットの 133 バイトは、BASIC が
どこからでも参照するため、切り替わる窓には置けません。ここでは除いています）。

追い出す量を増やすほど、追い出すための窓も大きくなります。単純に削除する場合の
4,096 バイトのほうが少なくて済みます。

⚠️ 以前の記述では 4,155 としていました。カセット命令の処理のサイズが古い値（350）の
ままだったためで、正しくは上の表の 389 です。どちらの値でも 5,947 を下回るため、
結論は変わりません（レビューで判明）。

内蔵プログラムの移動が容易だった理由は、それがデータであり、単一のコピーループ
（`$ADB8`）から読まれるだけだからです。BASIC を呼び返す対話的なコードではありません。
`BGTOOL` はこの条件を満たしません。`BgtFile_GoToScreen0` という自身のルーチンが、
範囲の外の `$AE96` にあります。

## ディスク版は 1 窓分低いところで同じ壁に当たります

RAM アダプタが提供するのは `$6000-$DFFF` の 32,768 バイトで、連続しています。
擬似ベクタが `$DFF6-$DFFF` に固定されています。窓の概念がないため、本体はどこからでも
始められます。

以下の数値はすべて実測値か、実測値からの引き算です。そのため答えではなく計算式を示します。

| 項目 | バイト | 出典 |
|---|---|---|
| RAM `$6000-$DFFF` | 32,768 | NESdev wiki [Family Computer Disk System](https://www.nesdev.org/wiki/Family_Computer_Disk_System) |
| 擬似ベクタ `$DFF6-$DFFF` | 10 | 同上。固定で移動できない |
| V3 の本体 `$8000-$CFFF` | 20,480 | 上記のラベル表 |
| ディスク版の `SAVE`/`LOAD` | 384 | `tools/fb-fds.py` の `SAVE_SIZE` |
| 起動処理と IRQ スタブ | 88 | 同ファイルの `V3_FDS_INIT` と `RTI` 1 個 |

```
32,768 − 10 = 32,758   利用可能（$6000-$DFF5）
20,480 + 384 + 88 = 20,952   ユーザーのプログラム以外の合計
32,758 − 20,952 = 11,806   プログラム領域（$6000-$8E1D）
```

⚠️ この先頭をページ境界に切り上げることはできません。切り上げると本体は
`$9000-$DFF5` になり、20,480 バイト必要なところに 20,470 バイトしかありません。
10 バイト不足します。本体を半端なアドレスから始めるか、10 バイトをどこかから
確保する必要があります。
（以前の記述では切り上げたうえに `$6000-$8FFF` 全体を空きとして数え、さらにディスク版
自身の 472 バイトを計算に入れていませんでした。レビューで判明）

16KB にする場合、本体は `$A000-$DFF5` の 16,374 バイトに収める必要がありますが、
必要なのは 20,952 バイトです。4,578 バイト不足します。

⚠️ これらは V3 の数値で、まだ誰も作っていない構成についての計算です。`fb-fds.py` は
どちらのバージョンからもディスクを作れますが、どちらも本体をカートリッジと同じ位置に
置いたまま `$6000-$7FFF` を使います。V2.1A で 8126 BYTES FREE、V3 で 8,182 バイトです。
上記の 11,806 バイトにするには本体全体を上へ移す必要があり、現在のディスク版が
行っている処理とは別の作業になります。

V2.1A ではこの作業は V3 より難しくなります。V2.1A の本体は `$8000-$DFFF` を埋めており、
`$E000` 以降を 11 か所から参照しています（V3 は 0 か所）。また、測定できている未使用領域は
1,522 バイトのメッセージ領域だけで、これは途中にあるため領域の拡張には使えません。

したがって、ディスクは見かけほど余裕のある媒体ではありません。カートリッジは本体を
ROM に置けますが、ディスクシステムには本体を置く ROM がないため、本体とプログラムが
同じ 32KB を共有します。

## マシン語を分割して置く場合は、不足する資源が変わります

マシン語は連続した領域を必要としないため、この場合の上限はアドレスの問題ではなくなります。
現在の 16KB 版で、ビルド結果から実測した値は次のとおりです。

| | バイト | |
|---|---|---|
| バンク 4 | 8,192 | すべて `$FF`（未使用）。`$5116` で `$C000-$DFFF` に切り替え可能 |
| バンク 7 の `$F553-$FFF9` | 2,727 | 常駐（`$E000-$FFFF` は切り替わらない）。内蔵プログラム 4 本目の残りで、ローダがバンク 3 の複製を読むため未使用 |
| フリーエリア | 16,374 | BASIC のプログラムと共有 |

呼び出す方法は簡単です。`CALL` は `jsr FrmEval` / `jmp ($0400)` なので、飛び先は
`$0400/$0401` の 2 バイト、つまり `POKE` 2 回で指定できます。NMI は最初から RAM 経由
（`$FFFA`→`$00ED`）なので、毎フレームの処理を差し込むのも `POKE` 2 回です。

切り替えには制約があります。`GAME` のローダは、切り替えたバンクの下半分に
`$C000-$CFFF` を複製し、切り替え中は NMI を禁止します。したがって 1 バンクで使えるのは、
コードが単独で完結するなら 8,192 バイト、BASIC の `$C000-$CFFF` を下に必要とするなら
4,096 バイトです。

つまり、オーバーレイを使えば ROM 側はマッパーの許す限り増やせます。代わりに不足するのは
常駐領域で、2,727 バイトしかありません。中継用のコード、割り込みハンドラ、入口の処理は、
切り替わらない場所に置く必要があります。

## 数値の上限はアドレスより先に来ます。V3 のほうが早く来ます

実機で測定しました（MiSTer・2026-08-25）。それぞれのディスクで 4 通りの書き方を
1 回ずつ入力しています。

```
V2.1A:  PEEK(50976) → 0      PEEK(-14560) → 0    PEEK(32767) → 0    PEEK(50976) → 0
V3   :  PEEK(54655) → ?OV    PEEK(-10881) → 0    PEEK(32767) → 0    PEEK(50976) → ?OV
```

同じ `50976` が V2.1A では通り、V3 ではオーバーフローします。したがって値ではなく
バージョンによる違いです。V3 の整数リテラルは符号付き 16 ビット（`-32768` から `32767`）、
V2.1A は `0` から `65535` です。符号付きの書き方は両方で同じバイトに届くため、実機の
検査では、バージョンで分岐せずに `PEEK(-10881)` を使っています。

この結果が意味することと、意味しないことがあります。

- これは入力できる数値の制限であって、到達できるアドレスの制限ではありません。
  `POKE`/`PEEK` はどちらでも全アドレスに届きます。アドレスを負の数として書くだけです。
  V3 で `$D57F` を扱うプログラムは `PEEK(-10881)` と書きます。内蔵プログラムが
  別の書き方を使っているのも同じ理由です（`GAME 0` の `PEEK(&H4016)`。`&` はファミリー
  ベーシックのキーボードにはある文字で、このプロジェクトのキー入力ツールにはありません）
- 空き容量の表示については何も分かりません。そちらは別の経路です。後述の
  「確認できていないこと」を参照してください

## 確認できていないこと

以下はすべて計算か推論であり、測定していません。確認する前に前提にしないでください。

1. **MMC5 が 24KB の連続した WRAM を割り当てられるかどうか。**
   [mmc5-wram-banks.ja.md](../reference/mmc5-wram-banks.ja.md) が扱っているのは `$5113` と
   `$5114`（`$6000-$7FFF` と `$8000-$9FFF`）で、`$A000-$BFFF` に RAM を置くレジスタは
   調べていません。ここは既に一度問題が起きている領域でもあります。16KB 版が起動時に
   判定しているのは、バンク番号の意味が実装によって異なるためです。

2. **実行中に窓の RAM と ROM を切り替えられるかどうか。**
   できるのであれば、`BGTOOL` の実行中だけ `$A000-$BFFF` をプログラム領域から借りて、
   終了時に返すことができます。その場合、何も削除せずに 24KB 版が成立します。

3. **`FRE(0)` と空き容量の表示が 32,767 を超えたときにどうなるか。**
   リテラルの側は上記のとおり測定しました。ただしそれはパーサの話で、表示は別の経路です。
   BASIC が値を計算して表示するもので、リテラルは関与しません。負になるのか、
   折り返すのか、別の表示になるのかは不明です。

   現在のどちらのビルドでも確認できません。ディスク版は約 11,806 バイト、16KB の
   カートリッジは 16,374 バイトが上限で、どちらも 32,767 に届きません。確認するには
   その値に届くビルドが必要で、それはこの文書が「まだ作れない」と説明しているものです。

   ⚠️ 以前の記述では、この 2 つの上限を「1 バイト違い」としていました。`$6000-$DFFF` の
   32,768 バイトをそのまま数えたためです。この文書のディスクの節が、そこから擬似ベクタを
   引く計算をしています（レビューで判明）。16 ビットの上限が問題になるのはカートリッジ側で、
   `$DFFF` より上にも RAM を割り当てる構成の場合です。

4. **`$5116` を `CALL` から操作したことがありません。**
   切り替えの経路は `GAME` のローダで実証されていますが、バンク 4 にコードを置いて
   実行した例はまだありません。上記の数値は「空であることを測定した」のであって、
   「使えることを測定した」ものではありません。

5. **V3 自体の未使用領域を測定していません。**
   これを正しく測れるのは `tools/fb-reach.py` ですが、V2.1A の SHA-1 に固定されています。
   `fb-disasm.py --gaps` が報告するのは「到達しなかった範囲」で、これは未使用とは別です。
   分岐表で解析が止まるため、`$C000-$DFFF` は明らかにコードがあるのに到達率 0% として
   報告されます。

## 測定をやり直す方法

```bash
# 全体の構成と、到達しなかった範囲
./tools/fb-disasm.py "Family BASIC V3 (Japan).nes" --gaps
./tools/fb-disasm.py "Family BASIC V3 (Japan).nes" --xref D400-DFFF

# 予約語の表（手書きの表ではなく ROM から読む）
./tools/fb-basic-to-sav.py --tokens "Family BASIC V3 (Japan).nes"
```

各範囲のサイズは上記のラベル表から求めています。あるラベルのアドレスから、別の用途に
属する次のラベルのアドレスを引いた値です。バンクの内容はビルド結果の `.nes` から
直接読みました。バンク 4 は 8,192 バイトがすべて `$FF` で、それ以外の値はありません。

リテラルの範囲だけは、ダンプではなく実機から得た数値です。実機に入力するツールは
このリポジトリに含まれていません。特定の MiSTer の接続設定に依存しており、公開する
リポジトリに置くべきものではないためです。測定を再現するには、4 通りの `PEEK` を
それぞれのディスクに手で入力するか、エミュレータで実行してください。結果は画面に
表示されます。
