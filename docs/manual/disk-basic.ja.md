# Disk BASIC の `SAVE` と `LOAD`

*ディスク版を操作する人のための文書です。作り方は [building.ja.md](building.ja.md) に
あります。*

[English](disk-basic.md)

ディスク版でも `SAVE` と `LOAD` の書式は元のままです。変わるのは保存先だけです。

## 1 枚に 1 本しか保存できません

ディスクに保存できるプログラムは 1 本です。もう一度保存すると前のものが置き換わります。
本体から操作できるのはこの 2 つの命令だけで、2 本を保存する方法も、ディスクの内容を
一覧する方法も、上書き以外に削除する方法もありません。

`LOAD` は名前でプログラムを選びません。ディスクにあるプログラムを読み込むだけで、
どんな名前を指定しても結果は同じです。

名前を付ける意味はあります。ディスクに記録され、ディスクを読むツールから見えます。
ただし、読み込むプログラムを選ぶためのものではありません。

## 書式

| 入力 | 保存先 |
|---|---|
| `SAVE "NAME"` / `LOAD "NAME"` | ディスク |
| `SAVE` / `LOAD`（引数なし） | ディスク（名前は `BASIC`） |
| `SAVE "DSK:NAME"` / `LOAD "DSK:NAME"` | ディスク（明示） |
| `SAVE "CAS:NAME"` / `LOAD "CAS:NAME"` | カセット（カートリッジ側のルーチンを使用。12 文字まで） |

## 名前の長さ

⚠️ どの用途でも名前は 16 文字までにしてください。

ディスクへ保存する場合は 8 文字までで、超えるとエラー `240` で拒否されます。
`LOAD` と `CAS:` にはこの検査がありません。名前は長さを確認する前にバッファへ
コピーされるため、長い名前はバッファの末尾を超えて書き込まれます。

現在確認している範囲では実害はありません。書き込まれた範囲をアドレスで名指ししている
命令は ROM 内に 1 つも無く、索引でそこへ届くのはコピー処理自身だけです。
31 文字程度を超えると、BASIC が文字列そのものを受け付けなくなります。

実機で測定した結果は次のとおりです。20 文字で 4 バイト、26 文字で 10 バイトが
バッファの外に書き込まれ、32 文字は受け付けられませんでした。いずれの場合も BASIC は
動作を続けています。これは未改造のファミリーベーシックと同じ動作で、ディスク版が
持ち込んだものではありません。16 文字までにしておけば問題になりません。

ディスクへ保存する場合の 8 文字という上限は、ディスクのファイルヘッダの名前欄が
8 バイトであるためです。

正確には次のとおりです。8 文字目より後ろの空白は無視され、空白以外の 9 文字目があると
拒否されます（エラー `240`）。ヘッダは短い名前を空白で 8 文字に埋めるため、
`SAVE "ABCDEFGH   "` は `SAVE "ABCDEFGH"` と同じ名前になり、どちらも保存できます。
`SAVE "ABCDEFGH X"` は 9 文字なので、切り詰められずに拒否されます。
名前の途中にある空白は残ります。`SAVE "A B"` は `A B` という名前で保存されます。

この 8 文字という制限はディスクへの保存だけに適用されます。`LOAD` は名前を参照しません。

`CAS:` は 12 文字までです。カートリッジ側のルーチンに渡す前に `CAS:` の部分を取り除く
必要があり、その処理が 12 バイトだけをコピーして残りを空白で埋めます。そのため、
カートリッジ自体は受け付ける 13〜16 文字の名前が、ディスク版では切り詰められます。
これはカセットの制限ではなく、ディスク版の `CAS:` の処理の制限です。

⚠️ `CAS:` は未検証です。手元のエミュレータにデータレコーダがないため、カセット側は
ルーチンに渡すところまでしか確認していません。カートリッジでの操作方法をそのまま
使えるように用意したもので、動作を確認したものではありません。

## 保存や読み込みが失敗した場合

画面には `?TP ERROR` と表示されます。カセット用のエラーを流用しています。専用の
エラーを追加するには BASIC のエラーテーブルを移動する必要があるためです。

実際の原因は数値で取得します。

```
PRINT PEEK(50976)
```

| 値 | 意味 |
|---|---|
| `0` | 直前の転送は成功 |
| `3` | ディスクが書き込み禁止 |
| `41` | ディスクが満杯 |
| `240` | 空白以外の 9 文字目がある（末尾の空白は無視される） |
| `241` | `LOAD` がディスクにプログラムを見つけられなかった |
| `255` | まだ一度も実行していない |

⚠️ V3 のディスクでは `PEEK(50976)` がオーバーフローします。V3 の整数リテラルは
符号付き 16 ビットのため、`PRINT PEEK(-14560)` と入力してください。同じアドレスです。
V2.1A はどちらの書き方でも動作します。

## 電源を入れ直してもプログラムは復元されません

ディスクは、何も保存していない状態と同じように起動します。空きメモリの表示も出ます。
プログラムは `LOAD` を実行したときに読み込まれます。

2026-08-24 まではこの動作が逆でした。当時のビルドを使っていた場合のために理由を書いておきます。
自動的に復元する処理は `8126 BYTES FREE` の表示を行う経路を通りません。そのため、
一度保存するとそのディスクでは空き容量が表示されなくなり、操作で戻す方法もありませんでした。
空き容量は `PRINT FRE(0)` でいつでも取得できます。

## カートリッジとの違い

| | カートリッジ | ディスク |
|---|---|---|
| 文字の絵 | CHR-ROM | CHR-RAM（ディスクから読み込む） |
| 内蔵プログラム | `$E000` 以降の ROM | なし（ディスクではこの領域が BIOS） |
| 電源投入時 | タイトルメニュー | GAME BASIC へ直接起動（`SYSTEM` でメニューへ移動可能） |

V3 のディスク版では `GAME` が使えず、実行すると `?SN ERROR` になります。内蔵プログラムの
置き場所が BIOS になっているためです。

グラフィックエディタはどちらの版にもありますが、入り方が異なります。V2.1A のディスク版は
`SYSTEM` から `2` を選ぶと `BG GRAPHIC` に入ります。V3 は `BGTOOL` 命令で起動します。

## PC からディスクの中身を読み書きする

`tools/fb-fds-file.py` を使うと、使用済みのディスクイメージの中身を PC から操作できます。

```
$ ./tools/fb-fds-file.py disk.fds --list
$ ./tools/fb-fds-file.py disk.fds --extract -o program.bas
$ ./tools/fb-fds-file.py disk.fds --insert program.bas -o new.fds
```

ほかに指定するものはありません。予約語はディスク内の BASIC から読み取ります。
ディスクは自身のインタプリタを持っており、プログラムを実行するのはそれなので、
その表以外は使えないためです。

`--insert` は保存済みのプログラムを置き換えます。2 本目を追加することはありません。
入力に指定したディスクを上書きすることも拒否するため、`-o` が必須です。

`--insert` は、問題のないディスクを拒否することがあります。長いプログラムを短いものに
置き換えると、古いプログラムの後半がディスクに残ります。これは意図した動作です。
`REM` には任意のバイトを置けるため、残った部分がファイルヘッダと同じ形になっている
場合があります。その状態で長いプログラムを入れようとすると、記録されていないファイルを
上書きするように見えます。残骸と実際のファイルはバイト列としては同じなので、区別できません。

拒否された場合は該当する位置が表示されます。その位置が自分の古いプログラムの内部だと
確認できる場合は、`--over-tail` を付けると上書きします。

### ディスクイメージの形式は 3 種類あります

| 形式 | 面の開始位置 | 作成するもの |
|---|---|---|
| 素の `.fds` | 0 | `fb-fds.py`、FDSKey（`.fds` を直接書き換え、元を `.fds.bak` として残す） |
| fwNES の `.fds` | 16（`FDS\x1a` の後ろ） | 他のツール |
| MiSTer の `.sav` | 16（16 バイトのゼロの後ろ） | MiSTer（ディスクとは別ファイル） |

拡張子ではなく、両方の位置でブロック 1 の署名を探して判別します。開始位置を誤ると、
別のプログラムの途中をファイルヘッダとして読むことになるためです。

解釈できなかったバイトは `\xNN` の形式で出力し、その個数を必ず報告します。
出力があったことと、内容をすべて解釈できたことを区別するためです。
